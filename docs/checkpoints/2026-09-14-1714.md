# Checkpoint — 2026-09-14 17:14

## Session summary

This session picked up right after committing and pushing the Low-integrity/MIC-based delete-boundary fix (commits `1f57556`..`855e23c`, already on `origin/main`). A second external review (much sharper than the first) then found that the MIC approach, while it closed "sandbox deletes an ordinary Medium file outside its boundary," left three real P0s: (1) two sandboxes on Low integrity with Low-labeled directories are mutually deletable — MIC is a linear order, it separates "sandboxed" from "not sandboxed" and nothing finer; (2) revoke/RW→RO/Protect never lowered the label back to Medium, so a directory kept its Low label — and thus its deletability by the granting sandbox — after access was withdrawn; (3) a sandbox whose label-writing failed silently kept running, sometimes at Medium, because the "was it labeled" check wasn't re-asked after every step that could hand over a new directory. All three were reproduced with real elevated `CreateProcessAsUser` processes before being accepted as real. Fixed #98 (the privilege gate asked about `SeSecurityPrivilege` globally instead of attempting the object-level `WRITE_OWNER`-gated write and reading the real result) and #99 (`--check`/`--explain` could report "refused" for a delete the real sandbox then performed, because `AccessCheck`'s simulation is stricter than the real kernel delete path under `WRITE_RESTRICTED`; fixed by reporting "cannot be established" instead of a false refusal, and by making the e2e `machineIsOpen` probe actually delete-and-restore rather than trust the simulation). Both were committed and pushed (`855e23c` is the tip).

The user then asked to actually solve peer isolation (#97) rather than document it as a known gap, explicitly open to requiring UAC on every configuration change (that's already the existing design — `--init`/`--grant`/`--add-dir` elevate; only `run` doesn't). A long design conversation with a third external "researcher" persona (relayed by the user, treated as an adversarial reviewer, not trusted blindly) converged on: **drop `WRITE_RESTRICTED` entirely and use a fully restricted token** (`CreateRestrictedToken` with no flags but `DISABLE_MAX_PRIVILEGE`), so the second access check applies to every operation including DELETE and `FILE_DELETE_CHILD`, not only writes. This closes peer isolation the same way it closes the original P0, because DELETE now has to go through the sandbox's own SID like anything else.

The catch, measured directly and repeatedly on this machine (not assumed): a fully restricted token's restricted list can't just be `{sandbox SID, Everyone, logon SID}` — without `BUILTIN\Users` in the list, System32/Program Files reads fail (`where.exe`, `git`, etc. die or can't find files), because those grant `Users`, not `Everyone`. So `Users` has to be in every sandbox's restricted list too, alongside a new machine-wide `wub-read` group (still to be built) for the one place neither `Everyone` nor `Users` covers: the user's own profile, which by Windows default grants only the owner's personal SID.

That created the real puzzle this session mostly spent its time on: if every sandbox's restricted list includes `Everyone` and `Users`, and directory B was granted to sandbox B in the ordinary way (or — the reviewer's key mandatory test — B's directory merely *inherited* `Users:Modify` from somewhere), does sandbox A (which also carries `Everyone`/`Users`) get to write/delete there too? Measured: **yes**, confirmed with a real elevated process (`scratch_claims_test.go`, since deleted). The fix attempted first — add explicit `DENY` entries for `Everyone`/`Users` on every granted directory, in the same `SetEntriesInAcl` call as the grant (`acl.Isolate`) — was measured to be **fundamentally broken**: `SetEntriesInAcl` canonicalizes deny-before-allow regardless of input array order, and even a hand-built raw ACL (via `InitializeAcl`/`AddAccessAllowedAce`/`AddAccessDeniedAce`, bypassing `SetEntriesInAcl` entirely) showed that **Windows honors any matching DENY over any matching ALLOW for the same token, regardless of physical ACE order** — confirmed with four separate minimal cases. Since sandbox B's own token also carries `Everyone`/`Users`, denying either of those SIDs blocks B from its own directory too. This is not a bug to route around, it's how NTFS DACL evaluation works.

The fix that was then found and verified to work correctly: **replace, don't deny**. Instead of adding a `DENY` for `Everyone`/`Users`, `Isolate` reuses the existing `listFor`'s clear-then-grant pattern to *replace* whatever `Everyone`/`Users` held on that path with read-only (`AccessReadExecute`), in the same `SetEntriesInAcl` call as the sandbox's own grant. No deny anywhere in the update, so there's nothing for the sandbox's own allow to lose to. Measured and confirmed with real restricted-token processes: sandbox A can no longer write or delete in B's directory (even one that started with `Everyone`/`Users: Modify`), reading is untouched (matches the "reads everything" promise — this was never restricted even before this work), and sandbox B still fully writes/deletes/reads its own directory. This is implemented in `internal/win/acl/set.go` as `acl.Isolate(path, account, entries, reach)` and is applied for **every** grant kind, not just writable ones — read-only grants have exactly the same inherited-`Users`-write hole, which the read-only refusal (targeted at the sandbox's own SID only) never covered.

Given the peer-isolation mechanism no longer needs Low integrity or mandatory labels at all (full restricted token + Isolate's replace-not-deny closes both the original P0 and the peer-isolation P0 together), the session is now in the middle of **ripping out the entire MIC/Low-integrity machinery** built in the previous session and replacing it with this simpler, actually-correct mechanism. This is a large mechanical revert across ~25 files (every `Labeled`/`ErrNotLabeled`/`acl.Applied`/`LabelInheritance`/`boundaryHolds`/`token.Restricted(..., low bool)` reference), interleaved with the new pieces (full restricted token with `Users` added and `WRITE_RESTRICTED` dropped, a new `wub-read` machine-wide group + one-time profile RX grant, `acl.Isolate` wired into `grant.Apply` for all kinds).

## Decisions

- Chose a fully restricted token (no `WRITE_RESTRICTED`) over Low integrity/MIC for the delete boundary, because MIC is a two-level order (sandboxed vs. not) and cannot separate peers from each other, while the second access check on a fully restricted token is keyed to each sandbox's own distinct SID.
- Chose to keep `Everyone` and `BUILTIN\Users` in every sandbox's restricted list (needed for window station and System32/Program Files reads, confirmed by direct measurement of process-start failures without them) rather than trying to remove them and provision system-wide read access through `wub-read` instead — the latter would mean rewriting ACLs across the whole OS estate, is far more invasive, and was not pursued once "replace, don't deny" proved that isolation doesn't actually require removing them from the list.
- Chose "replace Everyone/Users with read-only" over "deny Everyone/Users," after measuring that deny-based isolation is impossible in principle here: Windows honors any matching DENY over any matching ALLOW for the same token regardless of ACE order, and every sandbox's own token also carries Everyone/Users, so a deny for either would refuse the sandbox its own grant too. This was verified with a hand-built raw ACL (bypassing `SetEntriesInAcl`'s automatic canonicalization) to rule out "it's just an ordering bug in my code" before concluding it was a structural dead end.
- Chose to isolate on every grant kind (RW, RO, File, HomeTop), not only writable ones, after realizing mid-design that a read-only grant has exactly the same inherited-Users-write hole as a writable one, since the read-only refusal only ever targeted the sandbox's own SID.
- Declined to pursue window-station/desktop ACL manipulation (adding the sandbox SID directly, dropping Everyone) once the "replace, don't deny" mechanism proved sufficient for isolation without needing to remove Everyone from the restricted list at all.
