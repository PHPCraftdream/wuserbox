## Session summary

This session picked up from a checkpoint taken mid-work on the Windows file
boundary and ran through four consecutive rounds of external review, each
relayed verbatim by the user, plus one build failure that no review caught.

It began by finishing the task list the user asked for: a detailed in-program
manual. `wuserbox --help --all` now prints the overview, every command's entry
in full, the format of the rules file and the environment wuserbox sets and
reads — all rendered from one list of commands, so nothing is written twice.
The guard that makes it trustworthy is a test in each CLI package holding the
flags a command documents to the flags it really registers, in both directions.
That check immediately found two real drifts: `--ro` was registered on all four
directory commands and read by two, so `wuserbox --revoke <dir> --ro` parsed,
changed nothing and reported success; and `--audit` had been looking at
`BUILTIN\Users` as well as Everyone for a while while its entry still said
Everyone alone.

The first red CI of the session was a real product defect, not a flake: the
question `--check` asks Windows about creating a file demanded `FILE_TRAVERSE`
and `FILE_LIST_DIRECTORY` alongside `FILE_ADD_FILE`. Measured — a directory
handing out only `FILE_ADD_FILE` takes a new file, and traverse is bypassed by
`SeChangeNotifyPrivilege`, which `DISABLE_MAX_PRIVILEGE` keeps. The two extra
rights came from whatever the machine hands out ambiently, so it was invisible
wherever `%TEMP%` is generous and plain on a real Windows profile, which is
exactly where `--home-writes` is aimed.

Then the review rounds. Round one: three P0s of one shape — pinning a granted
directory copies other sandboxes' entries into it, and those copies answer to
nobody afterwards, so `FinishPending`, `--rm` and `Isolate`'s ordering each
needed `Prune` or a reordering. Round two: the sweep took the owner's own write
away inside a granted tree (#107 one level down), and junction and open-handle
behaviour were measured rather than assumed. Round three: an object with no
DACL at all — which Windows reads as everybody holding every right — was
invisible to narrowing, so a descendant carrying one stayed open to every
sandbox. Round four: the same absence at the *root* published a list naming the
sandbox alone, locking the owner out of their own directory.

Two review findings were rejected on measurement rather than opinion, and one
of those matters: the reviewer asked for the sandbox's own SID to be added when
a list-less protected descendant is normalised. Measured first — a protected
descendant with an *ordinary* list is equally unreachable and always was — and
making the change would have handed every granted home directory's `.ssh` to
the sandbox, since `acl.Protect` is what keeps it out. A guard now covers that
so a later "fix" is caught.

The build failure no review found: `internal/lock` crashed on CI twice with
`runtime.wirep(0x0)` and then `runtime.semawakeup`, and never once in thirty
local runs. `release()` was called twice — once early to prove another process
was waiting, once by a deferred call — and closed its handle both times. A
handle is a number Windows hands out again as soon as it is free, and the Go
runtime holds such numbers, one park event per thread; the second close reached
one of those. Proven by opening a sentinel file straight after the first
release, which takes the number just given up, and watching the second release
close it.

## Decisions

- Kept the tree sweep and accepted that a grant on a large tree costs roughly
  twice what it did, at the user's explicit choice.
- Asked for exactly what an operation needs when simulating it: a check that
  demands more than the deed is not stricter, it is wrong, and it called a
  working `--home-writes` grant broken.
- Read the whole tree before changing any of it, rather than rolling back. It
  is not atomic — the tree can change between the passes, and that is said in
  the comment rather than glossed — but the ordinary reason for stopping now
  happens before anything has moved.
- Refused to give the sandbox its own identifier on protected descendants. It
  would read as completeness and would hand over `.ssh`, `.aws`, `.netrc` and
  the rules file in any granted home directory.
- Kept the CI boundary step as an explicit list of test names rather than
  "fail on any skip in these packages": two tests there skip for honest
  reasons about the machine, and a check that turns red for those teaches
  people to ignore it. Added a count so a renamed test cannot pass it in
  silence.
- Pinned the CI Go version to `go.mod` after the runner silently moved to 1.27
  while the project declared 1.26. Not the cause of the crash, but the wrong
  thing to discover while reading one.
- Accepted, and wrote into the README, that two commands changing overlapping
  trees at once are not one operation. A global lock would close it and make
  every grant wait for every other.

## Open questions

- The two-pass sweep's window between reading and writing is real and
  unclosable without transactional ACLs. Worth revisiting only if Windows
  grows something better.
- `AppContainer` (measured: `System32` and `Program Files` grant
  `ALL APPLICATION PACKAGES`, a profile and ordinary data do not) would close
  the shared-writable limit by giving up "reads everything you can read". It
  stays a separate track, not a change to make on top of this one.
- What the sweep costs on a genuinely large tree has still not been measured,
  only reasoned about.
