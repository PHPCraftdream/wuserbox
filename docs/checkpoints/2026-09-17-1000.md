## Session summary

This session was five rounds of external review on the sandbox's two soft
spots -- the lease that keeps two runs of one sandbox apart, and the record
of what a run copied into a sandbox's profile -- followed by a layout pass
over the whole repository. Everything reported was reproduced against the
code before it was fixed, and every fix ends in a test that was seen failing
first.

The lease work moved in three steps, and two of them corrected a conclusion
rather than a defect. `PassTo` was handing the sandbox a duplicate made with
`DUPLICATE_SAME_ACCESS`, and the source handle is opened
`GENERIC_READ|GENERIC_WRITE`, so a program could set `FILE_ATTRIBUTE_READONLY`
on the slot file and brick `run`, `--init` and `--rm` for that sandbox until
somebody cleared the bit by hand. The duplicate now carries no access at all,
which is enough because the exclusion lives in the original open's share mode.
Inheritance was removed at the same time on the reasoning that a program
cannot outlive its stub -- and a later review showed that reasoning came from
a test that only looked at the final state. Asked properly, with a lease
racing the teardown, the slot is granted 0.9 to 1.7 ms after the kill, every
run. Restoring inheritance did not change that, and the reason turned out to
be that a process releases its handles before its process object signals: the
assertion was unachievable by construction. What the design actually needs is
whether the program can still execute at the grant, and measured through the
teardown it is down to one thread, the exit's own reaper. The inheritable
copy bought nothing measurable and was taken back out.

The record work was two reproduced data-loss cases and one regression of my
own. `union` folded the old list in front of the new one, so a partial copy
wrote back an entry without the exclusions the user had just added, and the
next `--no-ai` deleted what they protected. `copyEntries` skipped an entry
whose source had vanished without recording it, so the copy already in the
profile belonged to nobody -- and the fix for that overshot into claiming
paths this machine never had, which the next review caught. Only the previous
record can tell "vanished" from "never here", and `Copy` already had it in
hand. Separately, `depth: -1` was refused by validation only: with that bound
every mask falls out of reach, nothing is copied, and the mirroring removes
what the destination holds as stray. It is refused inside `Copy` now, and in
`forget`, because a record written by an older build reaches `Clear` by
another door.

Two gaps in my own method are worth recording. I merged the lease fix
believing a measurement that had not been taken, and it took an outside
reviewer to ask for the ordering. And when the operator made regression tests
a standing requirement, an audit of what had already landed found three live
behaviors nothing would have noticed the loss of -- `--rm` and `--init`
refusing a held slot, and the `--stub` guard's permissive side.

The session closed with a layout pass: every file over 500 lines split by
subject, which in Go means siblings in the same package, because a directory
is a package and splitting one would mean exporting the internals of a
security boundary.

## Decisions

- **The lease duplicate carries zero access.** The exclusion is the share
  mode of the original open, which any handle to the file object keeps, so a
  handle with no rights holds the place and can do nothing through it. Zero
  was sufficient on the first measurement and nothing weaker exists.
- **The inheritable copy was measured and taken back out.** It would have
  made the teardown ordering internal to the program's own exit rather than a
  race between two teardowns, which is arguably more robust — but it bought
  nothing measurable, and a change kept for the look of it is worse than no
  change. This is the one decision worth revisiting if the ordering ever
  fails on another machine.
- **A negative depth is refused by the copier, not only by validation**,
  because an ordinary run never calls `--config validate` and this limit
  fails open: it turns every protection the entry had off and reports success.
- **A missing source stays on the record only if the record already named
  it.** Taking a vanished copy back instead would act on a disappearance that
  is usually temporary; claiming a path that was never here takes files the
  sandbox wrote itself.
- **The line limit beats the entry guideline, and CONTRIBUTING now says so
  with the measurement.** `internal/policy/profile` went from 13 entries to 17
  by obeying the line limit; splitting the package would mean exporting
  `walk`, `copiesFile`, `matchMask`, `within`, `forget`.
- **`docs/checkpoints` stays flat.** `/resume` sorts every `.md` in that one
  directory by mtime; grouping by month would hide every checkpoint from the
  tool that exists to read them.

## Open questions

- **Why a sandbox cannot write its own registry** (#174). The hive wuserbox
  seeds is read-only to the account it was seeded for, while
  `HKCU\Software\Classes`, built by the profile service, accepts writes. The
  help promises the opposite. Cause is between `RegLoadAppKey` and
  `tightenHive`, never isolated, and no fresh administrator measurement has
  been taken.
- **Whether the teardown ordering holds on other machines.** The shipped
  arrangement passes because job1's kill of the program's threads beats the
  stub's handle-table close. That is two teardowns racing, not a kernel
  guarantee, and the new test is the only thing that would notice it ordering
  differently.
- **Whether a pool of slots is worth building.** Measured earlier: nothing
  breaks with two accounts, but credentials do not carry between them.
- **The latest review is stale.** It names `f54e6b9` and all three of its
  findings are closed by `b415fda` and `bf6b678`; it is worth asking the
  reviewer to re-run against `c46a2cf` before reading its release
  recommendation as current.
