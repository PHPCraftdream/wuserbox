**CI-greening arc.** The user asked to commit/push/confirm green CI for the already-local review chain. First push immediately failed: CI runs as the literal built-in Administrator (SID ending -500) on GitHub's windows-latest runner, which is itself a member of Administrators — a fact that broke a whole class of assumptions. Root mechanism, confirmed directly: `internal/win/proc/shield.go`'s `selfLockingDacl` denies the shielded-out account FIRST in its DACL, keeping an Administrators-allow entry only after it; when the account being shielded is itself an Administrators member, Windows' strict in-order ACE evaluation answers the deny before the allow is ever reached. This single mechanism explained the majority of the CI failures across several sessions of iteration:
- `internal/policy/grant`'s `TestApplyHoldsTheDirectoryItChanges` took its own lock via `lock.ForPath` directly instead of `lock.HoldTree`'s canonical-identity path Apply itself uses — unrelated to the admin-identity issue, a real test bug, fixed directly (`f6b8b3d`).
- Diagnostics-only commits (`7292699`, `7bd67c9`) added evidence-gathering to two still-unexplained CI-only failures (a thread-shut SetSecurityInfo refusal, an ACL OWNER RIGHTS control failure) rather than guessing fixes — both later resolved by real findings once evidence came in.
- Four+one shield tests (`internal/win/proc`, `internal/sandbox/exec`) were reseated from the test process's own identity into a real dedicated non-admin account (`RunAsAccount`), matching what a real run's stub actually has; a new `TestAdministratorsMembershipDoesNotUndoTheShut` pins the deny-before-allow ordering deliberately (`19e297f`, `0c05909`, `108b25f`, `f1478c3`).
