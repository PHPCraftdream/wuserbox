## Session summary

This session began with a release-readiness review and ended in the middle of
rebuilding how a sandbox is confined, because the review's one P0 turned out to
be the smaller of two problems.

The review found that a pre-existing hard link inside a granted tree handed the
sandbox write and delete on a file outside it — measured, with the sandbox's own
identifier turning up on the outside name. That was fixed by counting a file's
names before handing its directory over, then corrected twice: first because the
strict form (refuse any file with more than one name) refused the ordinary case —
on a real profile, 1312 files under `~/.config` and 4517 under `~/.claude` have a
second name, and every one of them is inside the same tree — and then because
comparing two spellings of one directory as strings refused a tree named in
8.3 form. Both corrections are guarded by tests watched failing first.

Then the user reported that agents could not work inside a sandbox at all. The
cause was not the hard-link check: **MSYS2/Cygwin programs cannot start under a
fully restricted token.** `bash.exe` dies before `main` with access denied on
kernel objects the runtime builds for itself. Measured twice, independently: the
runtime writes its own security descriptor naming the user, `SYSTEM` and the
administrators, then reopens its own object; the second access check a restricted
token gets finds no restricting identity in that descriptor. A sweep of every
identity that could be added to the restricting list showed only those three let
it through — and an access check over 5912 real objects showed that adding
`Administrators` makes 3892 objects writable and 3727 deletable, the user's whole
profile among them. So there is no fix from the token.

The decision, the user's, is to **give each sandbox a local account of its own**,
with the group it already has as its only member. That removes the whole class at
the source. Measured before building any of it: `bash`, `git` and PowerShell all
start under such an account; `CreateProcessWithLogonW` is the one launch call an
ordinary user can rely on and it needs the password every run; reads work through
`BUILTIN\Users` and `wub-read`; nothing extra has to be granted to start.

A second research pass settled the profile: neither "no profile" (no
`HKEY_CURRENT_USER` at all) nor "Windows-made profile" (a full one in
`C:\Users`) is acceptable, but seeding three values under `ProfileList` plus an
empty `NTUSER.DAT` makes Windows honour our own path and copy nothing. It also
found that a hive made with `RegLoadAppKey` grants `Everyone` full control, which
the profile service enforces once it is somebody's `HKEY_CURRENT_USER` — one
sandbox could write another's registry — so it is tightened during the elevated
step that already happens.

Four pieces are built and committed: the account with its DPAPI-sealed password,
the rules-file list of what to copy into a sandbox's profile, a job object that
stops a run's whole tree while leaving one Ctrl+C to the program, and a flake fix
in the file-publishing retry. Two agents are in flight: the thin profile and the
move of the launch itself onto the account.

## Decisions

- A sandbox becomes a local account per project. Rejected on measurement: any
  change to the restricting list (the only identities that work are the user's
  own by another name), a patched MSYS runtime (ties the tool to a forked
  toolchain, and selecting it through one agent's setting would tie it to that
  agent), AppContainer (cannot make the pipes at all), and a low integrity level
  (runs the shell, loses the boundary between one sandbox and another).
- The profile is ours, seeded so Windows builds nothing, and its registry hive's
  permissions are tightened before first use.
- Nothing is copied back from a sandbox's profile. A sandbox able to write into
  the files its credentials came from could rewrite them.
- The default copy list holds agents' own state directories and nothing on the
  sensitive list. An agent proposed including `~/.ssh`, `~/.netrc`, `~/.npmrc`
  and `~/.gitconfig`; those are exactly what the tool protects, and a default
  that copied them would have undone it for everybody at once.
- One Ctrl+C stays with the program; a second one within two seconds ends the
  job. The first version of that change put the child in its own process group,
  which disables Ctrl+C for it entirely — that would have killed an agent where
  the user meant to interrupt a turn.
- `--list` gains a long form rather than the project gaining a sixteenth command.

## Open questions
