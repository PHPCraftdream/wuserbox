## Session summary

This session began by resuming the previous one mid-rewrite: the MIC/Low-integrity
machinery was half stripped and the repository did not build. It finished that
rewrite (fully restricted token, `acl.Isolate` narrowing Everyone/BUILTIN\Users
instead of denying them, `wub-read` for profile reads), got everything green
unelevated and elevated, and pushed it as `865426d`. CI then failed on the GitHub
runner for a reason that does not reproduce locally: the runner keeps `%TEMP%`
inside a real Windows profile, which grants nothing past its owner, the system and
administrators, so tests that read an un-granted file beside a granted one failed.
That was fixed by making the end-to-end fixture state its ambient reading
permission explicitly (`73542f5`), and CI went green.

An external review then reproduced, with real child processes, that the peer
isolation claim was still false. Four findings, all confirmed here by measurement
before touching anything:

1. `SetEntriesInAcl` only edits an object's own list, so an entry a directory
   *above* handed down survived a grant, and Windows adds up every matching entry
   — a peer sandbox wrote and deleted inside another's granted directory. Fixed in
   `8ce4486` by walking the entries through `GetAce`, dropping the handed-down
   mark and writing the list back as the object's own (protected). A second cause
   turned up mid-fix: `GetExplicitEntriesFromAcl` returns only the object's own
   entries, so a first attempt built on it wiped the rest of the list.
2. `acl.Protect` had been given Everyone/Users read access by me earlier in the
   session so protected files stayed readable from inside a sandbox — which handed
   every other local account the owner's `.ssh` keys. Replaced with `wub-read`,
   a group nobody is a member of.
3. Granting a directory whose only write path was `Users:Modify` took the user's
   own write access away, outside the sandbox as well as inside.
4. `AccessCreateFiles` lacked `READ_CONTROL`, so `--home-writes` could not read
   what it granted. Found by CI, not locally, for the same `%TEMP%` reason.

A second review round then reproduced four more, three P0, one of them created by
the fix itself. All four were confirmed by measurement, fixed, and guarded:

1. **Revoke stopped reaching a frozen copy.** Pinning a granted directory copies
   what it was handed into its own entries — another sandbox's entry among them —
   and that copy answers to nobody once the directory stops inheriting. A revoked
   sandbox kept writing. Fixed with `grant.Prune`, which takes an account's own
   entries off everything under a revoked or narrowed path, except paths the record
   says the same account holds in its own right.
2. **An explicit entry on a descendant was never normalised**, inheritance on or
   off, because handing an entry down replaces only the handed-down part of a
   child's list. Fixed with `sweep`, which walks the granted tree and narrows the
   changing rights out of every object's own entries. The user was asked whether to
   keep this (it roughly doubles the cost of a grant on a large tree) and said keep
   it, with regression tests.
3. **`WRITE_DAC` was not counted as a changing right** by `writeMask`, so it
   survived normalisation and `--audit` reported nothing. A peer used it to grant
   Everyone full control and delete another sandbox's file. `writeMask` became
   `changing` and gained `WRITE_DAC`, `WRITE_OWNER`, `FILE_WRITE_EA`,
   `FILE_WRITE_ATTRIBUTES`.
4. **Narrowing assigned `AccessReadExecute`**, which hands reading to an entry that
   only covered writing — the same widening class this work was supposed to have
   closed. Now the changing rights are taken out of what is already there and an
   entry left with nothing is dropped. For `Modify` that lands on read-and-execute
   anyway, so the ordinary case is unchanged.

Every guard was checked by breaking the mechanism it guards and watching it fail
for the right reason, then restoring. The work from the second round is **not
committed**: the working tree holds it.

## Decisions

- Kept `Everyone` and `BUILTIN\Users` in every sandbox's restricted list and
  accepted that a shared-writable path which was never granted stays writable.
  Removing them would mean rewriting the ACL of the whole `C:\Windows` and
  `Program Files` trees, because reading a file is checked on the file. The
  guarantee was reworded to what is true: a sandbox cannot change what the machine
  does not already let every local account change, anywhere it was not handed.
- Kept the tree sweep rather than documenting the limit away, at the user's
  explicit choice, accepting that a grant on a large tree costs roughly twice what
  it did.
- Chose to pin a granted directory's list and make revocation tree-aware, rather
  than dropping other sandboxes' entries when pinning. Dropping would have been
  simpler and fail-closed, but it would silently cost a sandbox part of a grant it
  still holds, with no way for `init` to repair it.
- Used `wub-read` rather than `Everyone` wherever a sandbox needs to read
  something private: it has no members, so no ordinary token carries it, while a
  sandbox carries it among its restricting identifiers.
- Removed the "a delete refusal cannot be established" special case from `--check`
  after measuring that a fully restricted token gives that answer the same
  reliability as any other operation.
