## Session summary

This stretch was three waves of review on the two-process shape a run now
has, and the last wave found the thing the first two had missed.

The first wave closed four findings. `--init` built a sandbox's profile
with a plain `os.MkdirAll`, which follows a junction: measured, with a link
at `AppData`, both subdirectories were created inside whatever it pointed
at, by wuserbox, elevated, as the machine's owner. It now builds each
component through an `os.Root` and clears what is not a directory where one
belongs. Two neighbouring fears were measured and did **not** hold, so
nothing was changed for them: inheritable permissions do not propagate
through a junction (paired against a real child inside, which does get
them), and `os.RemoveAll` does not delete through one.

The shared-writable-directory limit was weighed properly and cannot be
closed: a write-restricted token would close it for writing and reopen
`DELETE`, which is the property the tool exists for. So the promise moved
instead — the README, the command's package comment and the general
`--help` now say what is actually guaranteed. `--audit` was found to print
"writable by Everyone, Users" about directories whose lists it simply could
not read, which landed hardest on other people's profiles; that answer is
now told apart from the other one.

The second wave raised the stub's process security as an unverified risk.
Measured, it was a P0: a program under the restricted token opened the stub
with every access there is and duplicated its token. `Shield` was written
for it — refuse the account on the process, the token's default list and
every running thread.

The third wave found `Shield` was still walked straight through, and was
right. Windows grants an object's owner `READ_CONTROL` and `WRITE_DAC`
whatever the list says, and both processes are owned by the same account:
the program opened the stub for `WRITE_DAC`, rewrote the list, took the
token, wore it, and `IsTokenRestricted` came back false. Closed with the
`OWNER RIGHTS` identifier, which is what limits an implicit grant. The
guard had missed it for a reason worth keeping: it asked for
`PROCESS_ALL_ACCESS`, was refused, and reported a process still open to
`WRITE_DAC` on its own. A refusal of a set is not a refusal of its members.
Every right is tried by itself now.

The same wave's P1s are all closed: the thread-shutting no longer treats
failures as success, the profile-rules migration no longer fires on a
credential file both lists name and now happens exactly once, a copy
stopped in the middle now comes back on the list that decides what to clear,
and the two newest boundary guards are in CI's no-skip list, which grew from
two packages to four.

The last thing in flight is a redesign the user asked for and I have only
planned: the `profile:` section should express directories, masks, depth and
exclusions, plus rules for clearing what is already in a sandbox's profile.
Seven tasks are on the list for it.

Part of the last of those tasks got written early, before the order of the
request was clear, and most of it was then thrown away rather than carried:
the help section and the file's own header describe a format that #159 is
about to change, and writing that prose twice is worse than writing it late.
What was kept is the half that does not depend on the format at all -- a run
that finds the rules file gone writes it back, which also stops a missing
file from reading as "copy nothing into the profile" in silence.

## Decisions

- The shared-writable-directory limit stays and the promise moves. A
  write-restricted token would close it for writing and put `DELETE` and
  `FILE_DELETE_CHILD` outside the second check, which is the property the
  tool exists to provide; an AppContainer closes it and costs "reads what
  you can read". Measured on an ordinary desk: 44 such directories, all but
  three under `C:\ProgramData`, whose root is stock Windows.
- `OWNER RIGHTS` rather than trying to refuse the owner directly. Ownership
  cannot be taken away and does not need to be — an owner who cannot rewrite
  the list cannot grant itself anything through it.
- The shield is measured on the shape (unrestricted parent, restricted
  child, same user, that user in the restricting list) and not on a real pair
  of accounts. The relationship is identical and a logon does not change
  process or thread object security, but that is reasoning, not measurement.
  It is the one place still standing on reasoning.
- The retirement of whole-directory profile rules is one-time, marked beside
  the bookkeeping rather than in the rules file. A migration that ran every
  time would undo a deliberate edit every time.
- The copy ceiling is 64 MB against a 254 KB default, and the budget is
  handed to the copier so a test can measure the refusal without asking the
  machine for 64 MB of temporary files.

## Open questions

- Two concurrent runs of the same sandbox. The new stub is visible to
  anything running as that account from the moment it is created until
  `Shield` runs, and a handle obtained in that window keeps its access
  afterwards. Raised in review, not yet reproduced, and not closable
  outright on an unprivileged run: `CreateProcessWithLogonW` takes no
  process attributes, so the initial list is not ours to set. What it buys
  an attacker is its own account without the second check — not the owner,
  not a peer sandbox.
- Whether `ktav` can carry a list of mixed shapes (a plain string or an
  object) through `LoadsInto`. The whole format in #159 depends on the
  answer and nothing has asked it yet.
- Whether the shipped default should name `.codex` with exclusions instead
  of two files. More useful and no longer 254 KB; #164 is to measure rather
  than guess.
