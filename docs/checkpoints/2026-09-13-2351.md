# Checkpoint — 2026-09-13 23:51

## Session summary

The user asked for a Windows utility that runs a program with restricted write
access, and this session built it from nothing to a released-shaped project:
`wuserbox`, written in Go, published at https://github.com/PHPCraftdream/wuserbox
(private). The mechanism was settled after a live experiment rather than from
memory: the command runs under the caller's own token, made write-restricted
with `CreateRestrictedToken`, and every project directory maps to a local group
whose NTFS entries decide where writing is allowed. The experiment also found
the non-obvious requirement that `Everyone` must be among the restricting
identifiers, or any program loading the window subsystem dies at startup with
0xC0000142.

Layout follows two rules the user set: at most seven entries per directory and
at most 700 lines per file, with roughly one exported symbol per file. The root
is at nine entries, which is two over: `LICENSE` and `.gitattributes` are both
load-bearing, and `docs/checkpoints/` from this checkpoint makes ten. That was
flagged to the user each time rather than hidden.

Three review rounds arrived from another agent. Every finding was verified
against the code before being accepted, all were real, and each fix landed with
a regression test. The third round exposed the most interesting defect: a
read-only grant only omitted the write bits, which does nothing against a write
inherited from a parent directory, so narrowing a nested folder changed nothing.
Fixing that surfaced a second defect underneath, that revoking an account's
entries removes permissions but leaves refusals behind.

Continuous integration exists and is now green on windows-latest: gofmt, vet,
golangci-lint with a curated linter set, and the tests. It failed at first on
every file because `.gitattributes` had been deleted earlier for the directory
limit, so checkout produced Windows line endings and gofmt rejected the tree.
The build machine then found a genuine product defect the local machine could
not: `check --operation delete` ignored the right to remove things from the
parent directory, so it reported a refusal where deletion actually succeeded.
Three tests that assumed a strict temporary directory now establish their
precondition and skip with a reason where the machine is more permissive.

Packaging is prepared but not exercised: GoReleaser for both Windows
architectures, a Scoop manifest pushed to a bucket repository, and an npm
package carrying the executable. No tag has been pushed, deliberately.

## Decisions

- Chose a write-restricted token over a separate Windows user account, because
  the user wanted the sandboxed program to keep their own environment,
  registry and credentials.
- Chose to keep the profile root read-only by default, rejecting the earlier
  design that handed it over, because a permission on a directory reaches the
  files already in it and would have made every dotfile writable.
- Chose to refuse a batch argument containing a quote rather than pass it
  through changed: doubling, backslash and caret escapes were each tried
  against a real script and none arrives intact.
- Chose to document that `--rw` and `--ro` last until revoked, rejecting
  cleanup after the run, because a permission that disappears only when a run
  ends tidily is a promise the tool cannot keep.
- Chose to make the delete check ask about the parent directory as well,
  after the build machine showed the previous answer contradicting reality.
