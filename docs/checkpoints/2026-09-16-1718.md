## Session summary

This session took the profile-copy format from a plan to something shipped,
and then spent the second half on the one reproduced escape, which is now
closed.

The format arrived in pieces, each delegated and each verified by hand: an
entry that carries depth, include and exclude masks; masks that carry a depth
of their own (the user's correction — one depth per entry cannot say "the
credentials at the top and the prompts wherever they are filed"); a copier
that honors all of it; a `cleanup:` section; validation and a `--dry-run`
preview that walks the same traversal the real copy does; and a default that
carries instructions — agents, commands, skills — and not just credentials,
measured at about 2.8 MB across 250 files against a 64 MB ceiling. A run now
skips a file whose source has not changed, which reversed a non-goal I had
written myself: the old argument refused to trust the destination's clock,
and missed that the comparison never has to read the destination at all.

The escape was the harder half. A stub is born with the account's
unrestricted token and Windows' default descriptor, and a program of a
*concurrent run of the same sandbox* can reach it before `Shield` runs. Two
things were believed and both were wrong. It is not token theft: measured
with a control, a restricted process wears a duplicated token only at
identification level and writes nothing. It is code injection —
`THREAD_SET_CONTEXT` into a process whose own token is unrestricted — and
that is the door the parent cannot shut, because `Shield`'s own thread pass
needs `OpenThread(WRITE_DAC)` and is refused once that access has been denied
to the same identity.

A consultation settled the rest by measurement: `STARTUPINFOEX` is refused by
`CreateProcessWithLogonW`, a job can no longer filter the token of what is
assigned to it, an integrity label shuts every door and kills MSYS on
`\BaseNamedObjects`, and taking the account SID out of the restricting list
shuts it and kills MSYS and PowerShell both. What is left is exhaustive: a run
is safe from a concurrent run if and only if no process of that account can
execute during the window, or the newborn's account is not the one any running
program holds. The fix shipped is the first branch — a run leases its sandbox
with one exclusive file handle, and the kernel gives the slot back when the
holder dies by any cause. `n = 1` is exactly "serialize whole runs"; raising it
is more accounts and a loop, not a second mechanism.

In flight right now: a fresh review reproduced four data-loss cases and an
output defect. Two agents are working them. The four are all one shape —
something that deletes does not honor the limit that governed what was
copied — except the fourth, which is an ordering bug I introduced with the
lease itself.

## Decisions

- **The escape is closed by removing what the attack needs, not by fighting
  it.** Four other routes were measured shut; the statement of the problem is
  an if-and-only-if, so there is no fifth to go looking for.
- **The lease is a file handle and not a mutex or a pid file**, because the
  kernel releases it when the holder dies by any cause: no stale state,
  nothing to time out, no cleanup that has to run on anybody's death.
- **A second run waits five seconds and then refuses.** Forever hangs a person
  silently behind an agent session that may last hours; refusing at once turns
  a benign overlap into an error about nothing.
- **A privilege was refused twice over.** `SeImpersonatePrivilege` granted to
  the user, or to the sandbox account, would close this — and it is the
  primitive behind the local-privilege-escalation family. Arming the account
  being contained would have turned a sandbox escape into a SYSTEM escape.
- **Duplicated profile entries whose limits differ are fatal**, not a warning:
  a rules file that quietly means something other than what it reads like is
  worse than one that is refused.
- **`Shielded` reads the DACL's protected bit rather than trying an open.**
  An administrator holding `SeDebugPrivilege` opens any process whatever the
  list says, so the open-and-see test measured the caller's rights and passed
  here while failing on CI.

## Open questions

- **Whether a pool of slots is worth building.** Measured: nothing breaks from
  two accounts, but credentials do not carry between them, because Credential
  Manager follows the loaded profile rather than the environment block. The
  recommendation was two slots with two preconditions, one if either fails.
- **Why a sandbox cannot write its own registry** (#174). The hive wuserbox
  seeds is read-only to the account it was seeded for; `HKCU\Software\Classes`,
  built by the profile service, accepts writes. The help promises the opposite.
  Cause is between `RegLoadAppKey` and `tightenHive` and was not isolated.
- **A lease held by a process that dies with job descendants still alive.**
  The release test covers a holder with no descendants. Named by the reviewer
  as a verification gap rather than a proven defect, and it is still a gap.
- **Whether the new regression test is stable on CI.** It passed once, in
  11.25s, and it is on the no-skip boundary list, so a skip will now fail the
  build rather than pass quietly.
