# Checkpoint — 2026-09-15 22:00

## Session summary

This session began with a review that said, plainly, that the tool could not
be released as file protection yet, and it ended with the one measurement
that decides the shape of the fix.

Four of the review's findings were verified here rather than taken on trust,
and all four held. The worst was not a permission hole at all: a sandbox owns
its own profile and needs no privilege to make a junction, so it could
replace a listed directory with one and have **wuserbox itself** — running as
the machine's owner, with their rights — delete and overwrite whatever it
pointed at on the next run. Reproduced on a real junction: a file outside the
profile deleted, another truncated. Fixed by routing every write and delete
through an `os.Root` pinned on the profile, measured to refuse traversal
through a junction while still allowing the link itself to be removed. A
sandbox that plants one no longer pins that name forever either: what is not
a directory where a directory belongs is cleared first, which is safe exactly
because removing a link is not following it.

The second was usability and was mine. The default profile list named whole
agent state directories, and I wired the copying without measuring what that
list came to: **72,320 files and 19,436 MB into every sandbox on every run**,
almost none of it credentials — 10 GB of `.claude` transcripts, 7.2 GB of
`.codex` SQLite history, and 82 MB of a note-taking app inside `.config`. The
default now names credential and settings *files*: 17 entries, 254 KB on this
machine. Two tests hold the shape — the list may not name a tree, and a name
is refused by its first segment so a file inside a protected directory is
protected with it.

The other two were smaller and are closed: sandbox accounts kept their
membership of the machine-wide `wub-read` forever (`RemoveMember` existed and
nothing called it), and `--rm` could strand a profile no later attempt would
ever come back for.

Then the real question. Since the account migration, the account and the
restricted token have been treated as alternatives, because the token was
what MSYS could not start under. An `fm` agent measured the analog on this
machine and found the reading was wrong — and found the root one object
earlier than the project believed: the MSYS runtime cannot query **its own
process token**, whose descriptor names the user, and the user's SID can
never be a restricting one. Under an account that descriptor names the
account, which *can* be. Its control run with the old list reproduced the
historical death on the same machine.

CI then answered it for real, on real accounts, under the no-skip check:
`bash` starts under a token restricted to the sandbox's own identities, the
sandbox still writes what it was granted, and a directory granted only to
`INTERACTIVE` is refused — paired with the same write succeeding under the
plain account, so the refusal cannot pass for the wrong reason.

So the account and the restricted token are complementary. Nothing is
switched over yet: `runAsAccount` still launches the program directly, and
the stub in the tests is the test binary re-executing itself.

## Decisions

- The crowd-SID class is closed by putting the second access check back, not
  by extending a list of SIDs. An interactive token carries at least nine
  such identities here (`INTERACTIVE`, `CONSOLE LOGON`, `LOCAL`, `This
  Organization`, `Local account`, `NTLM Authentication` beyond the three
  handled), plus machine-specific ones the agent found in its own token, so
  any list is wrong by construction. Rejected: hard-coding more names, and
  deriving the list from the account's token — the honest version of the
  second is the first written backwards.
- Restricting SIDs over deny-only groups. Measured to compute the same access
  predicate, so the choice was allow-list versus deny-list: the allow-list
  is already `token.Restricted`, already covered by the boundary tests, and
  leaves `IsTokenRestricted` true so `InsideSandbox` keeps its kernel answer.
- `token.AsSandbox` is a separate function from `Restricted` on purpose. The
  same addition — the token's own user SID — is safe in one and catastrophic
  in the other, because `Restricted` cuts down the owner's token.
- The default copy list names files, never directories, and the `stat` is for
  a regular file: a name that happens to be a directory on somebody's machine
  would otherwise be copied whole.
- `--rm` deletes the account last and only when nothing still names it; the
  profile directory is cleared whether or not an account was there.
- Building a sandbox as a standard user is refused with a diagnosis rather
  than fixed. The fix needs a password to cross a process boundary on disk,
  which cannot be measured on a machine whose only user is an administrator.

## Open questions

- Whether one Ctrl+C still reaches the program through two nested jobs and
  two interrupt handlers once the stub is in the chain, and whether a second
  still ends the run. Not measured; #156.
- Whether `wuserbox.exe` installed into a profile can be started by the
  sandbox account at all. CI showed the symptom already — the first stub run
  failed with "access is denied" before any token work, because the binary
  sat in the runner's own temp — so `--init` has to check this and say so.
- Whether reads that today depend on `Authenticated Users` or `INTERACTIVE`
  break once the second check returns. Same limit the old design had, but it
  has not been swept for.
