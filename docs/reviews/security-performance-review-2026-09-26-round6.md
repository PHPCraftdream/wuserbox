## P1-1 — Go-owned SID теряет владельца памяти до Windows-вызова

**Статус:** новая находка старого кода. **Confidence:** высокая для нарушения
lifetime; практическая частота и управляемое расширение прав не измерены.

**Evidence.** `internal/win/sid/current.go:31` получает TOKEN_USER в `[]byte`.
На `:35` SID извлекается как `uintptr` и передаётся в обычную Go-функцию
`format`. После этого чтения `buf` больше нигде не используется.
`internal/win/sid/sid.go:53–57` делает то же с `Value`: превращает `&v[0]`
в число и возвращает `format(...)`. `format` на `:99–105` получает только
число, затем выделяет память и вызывает `ConvertSidToStringSidW`.

Проверка `go build -gcflags='-live' ./internal/win/sid` на объявленном Go 1.26.0
завершилась с кодом 0. Существенная строка вывода:

```text
current.go:35:15: live at call to .../sid.format: .autotmp_57 ~r0 ~r1
```

`buf.ptr` здесь уже отсутствует; при предшествующем `GetTokenInformation`
compiler считал его live. Это проверка реальной liveness, а не только поиск
отсутствующего слова `KeepAlive`.

`uintptr` не удерживает Go-объект и не обновляется при перемещении. Специальное
правило удержания указателя при системном вызове требует преобразования
в самом выражении вызова; промежуточный Go helper с параметром `uintptr`
этого контракта не получает. [Правила unsafe.Pointer](https://pkg.go.dev/unsafe#Pointer).
Выделение памяти внутри `format` даёт точку, в которой больше нельзя
полагаться на прежнюю достижимость буфера. Возможное размещение backing
storage на стеке дополнительно требует корректного указательного типа,
а не сохранения адреса в числе между Go-вызовами.

**Impact.** Чтение SID из памяти без гарантированного времени жизни может
дать отказ Windows, неверную строку или native fault. Это центральный
поставщик identity для токенов, владельца ACL, групп чтения и state.
`format` также превращает неуспех Windows в пустую строку, а `CurrentUser`
возвращает её с `nil` error — ошибка identity теряет причину.
Доказательства воспроизводимого побега или получения SID другого пользователя
нет; такой вывод из compiler output делать нельзя.

**Recommendation.** Удерживать владельца буфера до последнего потребителя;
на границе обычных Go-функций передавать типизированный указатель, а
преобразовывать его в `uintptr` непосредственно в Windows-вызове. Для
TOKEN_USER предпочтителен typed token/SID helper с понятным владением
backing storage; завершающий `runtime.KeepAlive` должен удерживать именно
это storage. Не заменять исправление глобальным pin на весь процесс.
Сохранить ошибку форматирования и запрещать успешную пустую identity.

**Tests.** Проверить compiler liveness после исправления и адресные
token/current-user tests; добавить отказ formatter с проверкой непустой
ошибки. Нынешние счётчики `sid.Parses/Frees` эту ошибку не видят: здесь
нет ни `sid.Parse`, ни native SID, выделенного этим API. Нагрузочный GC-прогон
или программа воспроизведения нарушения границы в этом ревью не выполнялись.

## P2-1 — неочищенная копия забывается после обычной ошибки открытия

**Статус:** регрессия `f3209ca`. **Confidence:** высокая, измерено на TempDir.

**Evidence.** `internal/policy/profile/forget.go:190–192` добавляет fast-path
для bare entry: если `lookAt` не прочитал объект, возвращается `(false, nil)`.
`mirror.go:209–212` превращает **любую** ошибку `root.Lstat` в `readable=false`,
а не только `IsNotExist`. Ветка с ограниченным entry на `forget.go:203–205`
также считает любой такой отказ отсутствием.

Маленькая проверка держала только собственный временный файл обычным
exclusive handle. Получено:

```text
root.Lstat: sharing violation
clearEntry: taken=false, error=nil
Copy: entries=0, error=nil
после закрытия handle: файл существует, прежнее содержимое сохранено
```

Проверен и `clearEntry`, и настоящий `Copy` с прежним record и пустым новым
profile-списком. Никаких прав или записей пользователя тест не менял.

**Impact.** `fillProfile` на `internal/cli/setup/run.go:158–175` принимает
успешный `Copy`, сохраняет только новый список и теряет запись об оставшемся
файле. После освобождения временного handle следующий запуск уже не знает,
что эту копию следовало убрать. То же ложное завершение опасно для `--no-ai`:
отозванные конфигурационные/credential-копии остаются в профиле. Это ошибка
очистки и учёта, не запись за пределами файловой границы.

**Recommendation.** Различать «объект отсутствует» и «не удалось узнать».
Только `IsNotExist` разрешает successful no-op; остальные ошибки должны
останавливать cleanup, оставляя запись для повторной попытки. Флаг мутации
нужно вычислять отдельно от успеха удаления.

**Tests.** Закрепить locked destination в public Copy/Clear flow: операция
возвращает ошибку и прежний record остаётся доступен для retry; после
освобождения handle retry удаляет копию. Отдельно сохранить текущий тест
«файла уже нет», который действительно должен оставаться no-op.

## P2-2 — обещание SandboxGroup не доходит до member lookup

**Статус:** остаточный fail-closed контракт; прежний `NoneMapped` уже закрыт.
**Confidence:** высокая для ветвления, средняя для практической значимости.

**Evidence.** `owner.go:306–330` различает `SandboxGroup` и `IdentifierAlone`
при разрешении SID в имя. На `:331` оба вызывают один `localGroupMembers`,
а на `:394–395` `ERROR_NO_SUCH_ALIAS` / `NERR_GroupNotFound` безусловно
возвращают пустой список без ошибки. Требование существующей sandbox group
на этой стадии больше не проверяется.

**Impact.** Если группа пропала или изменила имя между двумя SAM-вопросами,
операция может продолжить работу только с group SID, потеряв account SID
в owner comparisons. Для произвольного standalone SID такое поведение
ожидаемо; для обещанной существующей группы ответ противоречит контракту
нового `Identity`. У обычной неизменной локальной группы этот путь не
ожидается. Песочница не получила права удалять собственную SAM-группу;
подтверждённого управляемого из restricted-процесса триггера здесь нет,
поэтому этот более узкий случай не объявлен P0/P1.

**Recommendation.** Сохранить различие двух режимов и при member lookup:
группа, отсутствие которой неожиданно, должна отказать до ACL walk.
Standalone-ветвь может принимать отсутствие локальной группы. По возможности
получать member SIDs напрямую, сохранив точную identity, а не переводя их
в имена и обратно.

**Tests.** Адресный unit test второй стадии: имя группы разрешилось,
member lookup сообщает её отсутствие, `SandboxGroup` не получает usable
identities и не пишет ACL. Отдельный standalone-контроль остаётся успешным.
Нынешние новые тесты инъецируют отказ первой стадии и этот ответ не проверяют.

## P2-3 — повторный HomeTop передаёт дочерним owner-capped объектам флаги родителя

**Статус:** найдено статически; фактическая DACL и отказ записи под настоящей
учёткой в этом раунде не измерены. **Confidence:** высокая для переноса flags,
средняя для полного пользовательского сценария.

**Evidence.** `internal/policy/grant/kind.go:41–45` задаёт HomeTop как
создание на корне и `Modify` с `OBJECT_INHERIT | INHERIT_ONLY | NO_PROPAGATE`.
`acl/isolate.go:166–180` собирает один `hand` из всех наследуемых записей
корня и передаёт его всему sweep. `owner.go:490–496,597–615` записывает
этот `hand` в полную защищённую DACL sandbox-owned потомка без преобразования
flags по типу объекта и глубине. Параметр `reach` в `Isolate` не используется.

Windows превращает подходящую унаследованную запись на файле в effective
ACE; явная копия исходной `INHERIT_ONLY` — другое представление прав.
`NO_PROPAGATE` также должен исчерпываться на непосредственных детях, а не
начинаться заново на каждом уровне. [Правила наследования ACE](https://learn.microsoft.com/en-us/windows/win32/secauthz/ace-inheritance-rules).

**Impact.** После того как HomeTop уже позволил песочнице создать файл,
повторный init/reapply может заменить effective право этого файла
родительской inherit-only записью и оставить owner cap только на чтение.
Это объясняет риск «сам создал, после восстановления больше не пишет»
для HomeTop. Перенос ограниченных по глубине записей на всех потомков
также не следует считать эквивалентным обычному наследованию.
Обычный RW (`OI|CI` без `IO/NP`) этой конкретной причиной не опровергается;
новый побег здесь не заявляется.

**Recommendation.** Перед owner-cap получать effective/inheritable записи
для конкретного дочернего типа и глубины; сохранить заданную область
HomeTop. Не убирать owner cap и не заменять защищённые ACL широким Full
Control ради исправления совместимости.

**Tests.** Нужен lifecycle-контроль HomeTop: существующий файл, созданный
песочницей, остаётся редактируемым после повторного grant/init; соседнее
поддерево по-прежнему не получает этот grant. Нынешние HomeTop e2e в
`internal/e2e/reach_test.go:159,198` проверяют выдачу и создание после неё,
но не owner-capped reapply уже созданного файла. Это адресная проверка
для account-chain CI, не причина запускать локально административные прогоны.

## P2-4 — второй оператор одного проекта может пересоздать учётку первого

**Статус:** статическая lifecycle-находка вне сценария одного оператора.
**Confidence:** высокая для последовательности кода; измерения с двумя
административными учётками не выполнялись.

**Evidence.** `internal/sandbox/name.go:21–52,121–124` выводит group из
канонического проекта без SID оператора; `existingName` также ищет глобальную
machine group только по проекту. `account.NameFor` производит account из
этой group. Record и profile, напротив, находятся в личном StateDir оператора.

При первом init другим оператором его собственного record нет.
`sandbox/init.go:285–319` находит уже существующий account, а `BelongsTo`
проверяет группу и project comment, но не создателя. Затем
`replaceUnopenableAccount` на `:333–348` видит пустой `s.Secret`, считает
account восстановлением потерянного пароля и удаляет его перед созданием нового.

**Impact.** Это возможно при последовательных запусках двух операторов,
без гонки. У первого остаются старые password seal и файлы старого owner SID,
а сам account уже заменён. Его следующий logon перестаёт работать;
отдельные owner ACL существующих файлов также требуют восстановления.
`docs/limits.md:121–143` описывает только одновременную гонку ACL и утверждает,
что accounts/operators независимы, — этого ограничения для такого случая
недостаточно. Это действие доверенного администратора через обычный init,
не доказательство повышения прав из sandbox.

**Recommendation.** До автоматического удаления существующего account
проверять, что он создан этим оператором. Минимальный безопасный вариант —
отказ с ясным указанием чужого/неустановленного владельца и отдельный явный
recovery flow. Полноценная поддержка нескольких операторов потребует
operator identity в machine namespace или machine-wide ownership metadata.
Одного расширения tree-lock недостаточно: последовательные вызовы тоже конфликтуют.

**Tests.** Table-driven проверка ownership decision без создания пользователей:
общий project/group, разные operator SID, второй init отказывает **до** Delete.
Проверка восстановления собственной потерянной записи должна остаться отдельно.

## P3-1 — реальные частичные удаления profile entries остаются Θ(E²)

**Статус:** возможность оптимизации, не регрессия исправленного unchanged warm-copy.
**Confidence:** высокая, измерено маленьким тестом.

**Evidence.** `forget.go:63–65` строит полный индекс current entries,
`:117–132` сбрасывает его после каждого реального удаления. Если из E старых
entries удалить половину, оставив половину действующими, следующий stale entry
заново индексирует всю оставшуюся половину и читает directory snapshot.

| Старых entries E | Resolver instances | Place resolutions | Обработано children |
| --- | --- | --- | --- |
| 4 | 2 | 6 | 7 |
| 8 | 4 | 20 | 26 |

Все файлы теста состояли из четырёх байт; после `forget` удалённые entries
действительно отсутствовали, сохранённые оставались. Для E=2k получается
k перестроений, k(k+1) resolutions и сумма размеров k snapshots.
Это вычислительная цена редактирования списка/реальной очистки; после записи
нового record следующий неизменный запуск уже не платит её снова.

**Recommendation.** Отдельно учитывать стабильный набор имён, которые надо
сохранить, и инвалидировать snapshots затронутых каталогов после известного
удаления. Либо предварительно разрешить keep-list, а перед destructive action
проверять только затронутые identities. Нельзя просто отменить инвалидацию:
создание/удаление/замена link действительно меняет ответы resolver.

**Tests.** Сохранить контроль результата очистки и считать resolutions/children
на 4/8 entries; отдельно проверить алиасы и реальную мутацию между вопросами.
Большой нагрузочный benchmark для установления этой сложности не нужен.

## P3-2 — warm preparation повторно разрешает одни и те же grant paths попарно

**Статус:** дополнительная возможность снизить O и аллокации вне profile-copy.
**Confidence:** высокая для сложности; время на больших списках не измерено.

**Evidence.** `sandbox/grants/extra.go:40–58` вызывает Add для каждого
конфигурационного grant на обычном prepare. `state/grants.go:26–33,73–87`
каждый раз линейно ищет его в `s.Grants`. Даже unchanged fast-path сначала
платит за этот поиск. `config/lookup.go:31–47` для каждой пары снова делает
Resolve/Key обеих сторон с файловыми открытиями и новыми строками.
При R rules и G grants это O(R·G) сравнений/разрешений; при R≈G — квадрат.

**Impact.** При большом явном списке разрешённых каталогов это замедляет
каждый запуск даже без ACL sweep и без перемещения profile bytes. При двух-трёх
grants цена мала; цифры ускорения без измерения не заявляются.

**Recommendation.** Operation-local индекс канонических keys и кеш разрешения
аргумента под текущей блокировкой: O(G+R) разрешений вместо O(R·G), с явной
инвалидацией при изменении списка/namespace. Сохранить filesystem identity,
missing-path и неоднозначные Unicode случаи; глобальный strings.ToLower
не является заменой. Дополнительно можно мемоизировать решения `sandboxGroup`
на один revoke: `acl/reclaim.go:201–243` разрешает повторяющиеся trustee SID
по имени заново на каждом объекте.

**Tests.** Маленькие 4/8 grant fixtures с совпадающими unchanged grants и
счётчиком разрешений, без реального повторного применения ACL. Сохранить
действующие Unicode/alias/lifecycle guards. Оптимизацию отделить от исправления
fail-closed ветвей: дешёвый ответ должен быть тем же ответом.

## Покрытие основных границ и пределы вывода

Прослежены account → stub → fully restricted token, три console-path,
Shield/process/thread/default DACL, jobs и передача lease, stdio/relay
drain/resize, ACL grant/revoke/Prune/owner cap, path identity и hard links,
profile creation/copy/cleanup, state/config, check/audit и workflows.

- Native descriptor owner-UAF предыдущих раундов по прежнему пути не найден:
  `readable` принимает решение до Free, а operation-owned identities держат
  parsed SID и member buffers до End. Это не устраняет P1-1 другого helper.
- `claimClose` выполняется до запуска close worker; resize регистрируется
  под mutex, закрытие ждёт уже зарегистрированные операции. Семь адресных
  console-free tests ownership/ordering и birth guard PASS. Реальные conhost
  permissions подтверждаются account-chain, который на этом SHA в CI не работал.
- Ошибка birth console enumeration не считается автоматически отсутствием
  консоли; unknown результаты conhost oracle сохраняются. Три обычных
  verdict tests PASS. Тесты own-console по workflow требуют отдельного opt-in.
- Jobs создаются до запуска и присваиваются suspended child; outer job
  закрывается перед bridge drain. Lease берётся до profile fill, передаётся
  stub без полезных прав и без дальнейшего наследования. Нового подтверждённого
  нарушения этих свойств чтение не выявило.
- Profile writes/cleanup используют os.Root. Hard-link enumeration теперь
  отличает EOF от ошибки и отказывает при неизвестном результате; grant
  preflight идёт до ACL publish. Права проверяются на момент операции,
  уже открытые handles не отзываются — прежний документированный предел.
- `--check` получает account token либо уже работающий токен той же учётки;
  `--audit` читает DACL один раз на объект в WritablePass, отделяет unknown
  от writable и исключает inherit-only при вопросе о самом объекте.
- Release и CI берут Go из go.mod. В goreleaser `before` есть `go test ./...`;
  утверждать, что release вовсе не запускает тестов, было бы неверно.
  Но отдельные CI gates с запретом SKIP и own-console measurement этим hook
  не заменяются, а текущий exact-SHA CI не стартовал.

Общие Everyone/Users-writable каталоги, сеть и общий desktop не превращены
этим ревью в закрытую границу: README/limits прямо оставляют их вне полной
изоляции. Находок, позволяющих объявить этот срез защитой от любых действий
враждебного процесса на всей машине, нет.

## Приоритет до выпуска

1. Исправить P1-1 и закрепить lifetime/error propagation regression.
2. Устранить измеренный P2-1, чтобы успешная очистка снова означала отсутствие
   снятой копии либо сохранённый record для retry.
3. Закрыть group-membership отказ P2-2; измерить и исправить owner-capped
   HomeTop reapply P2-3. Для нескольких операторов нужен отказ/ownership
   guard из P2-4 либо явное ограничение поддержки с запретом опасного recovery.
4. Получить зелёный CI финального SHA с обязательными account/boundary,
   hive и own-console проверками после устранения инфраструктурной остановки.
5. Оптимизировать P3 отдельно. Warm-copy и scratch уже улучшены; полный ACL
   preflight нельзя пропустить ради O(1) без смены доказательства границы.
