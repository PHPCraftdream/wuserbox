## P0-1 — alreadyCapped принимает лишние разрешения за готовую политику

Места: `internal/win/acl/owner.go:316`, `:348`,
`internal/win/acl/sweep.go:224`, `:292`.

Исправление `capPresent` проверяет дополнительные разрешения именно
`OWNER RIGHTS`. Это закрывает точную форму P0 из раунда 4. Однако
`alreadyCapped` по-прежнему проверяет только наличие ожидаемых записей
родителя и корректного owner-cap. Отсутствие лишних разрешений для других
SID не проверяется.

В результате самостоятельно защищённый дочерний каталог, принадлежащий
песочнице, может содержать весь ожидаемый набор вместе с дополнительным
широким разрешением `Everyone`. `narrowOwn` вычисляет удаление этого
разрешения, но `capObject` возвращает успех по fast path, не применяя
вычисленное сужение. Защищённый DACL дочернего каталога затем не меняется
при публикации родителя.

**Подтверждение:** диагностический тест вызвал настоящий публичный
`acl.Isolate` на временном дереве. Владение объектами проверялось по
security descriptor, а не предполагалось. В контрольном дочернем каталоге
ожидаемый набор отличался, поэтому сработала обычная перезапись. В
проверяемом — совпадал, поэтому сработал fast path. Для обоих `Isolate`
завершился успешно.

| Проверка после успешного Isolate | Контроль: обычная перезапись | Совпавший набор плюс лишнее разрешение |
| --- | --- | --- |
| Everyone всё ещё имеет изменяющие права | нет | да |
| Новое открытие каталога на WRITE_DAC | отказ | успех |
| Windows AccessCheck на запись с другим restricting SID | отказ | разрешено |

Открывался новый handle после завершения операции. Старые handles не
участвовали. Последняя строка измерена через production `access.Check` и
fully restricted token с другим SID; полного logon двух новых локальных
учёток в этом раунде не было. Это ограничение стенда, а не предположение о
сохранении ACE: сохранение прав и возможность нового открытия измерены.

**Влияние:** дерево, объявленное изолированным, остаётся изменяемым через
общий SID; владелец сохраняет доступ к изменению DACL. Это нарушение
изоляции *внутри выданного дерева*. Документированное исключение для
общедоступных каталогов вне выдачи здесь неприменимо: `docs/limits.md`
прямо обещает их сужение внутри выданного дерева и закрытие расширенных
прав следующим sweep.

**Регрессия:** `TestTakingBackRepairsAnExtraOwnerRightsGrant` проверяет
дополнительный OWNER RIGHTS grant при `TakeBack`, а не дополнительный SID
при `Isolate`. Существующие тесты обычного повторного sweep не создают
комбинацию «все ожидаемые ACE уже есть, плюс лишнее разрешение». Постоянного
теста этой комбинации нет.

**Исправление:** исключить ранний успех по подмножеству ожидаемых ACE.
Либо сравнивать весь нормализованный итоговый DACL, либо выполнять
нормализацию без такого fast path. Отдельно проверить дополнительные
разрешения Everyone, Users и самой учётки, сохранив права оператора.
Приёмочный тест должен измерять отказ новой операции другой реальной
песочницы после успешной выдачи и входить в обязательный boundary-список.

## P0-2 — Unicode folding объединяет разные каталоги на файловой границе

Основные места: `internal/win/acl/links.go:90`, `:100`.
Та же ошибка идентификации: `internal/sandbox/name.go:27`,
`internal/sandbox/init.go:76`, `:83`, `:92`, `:120`.

`insideOnly` получает реальные имена hard links, но затем `within` решает,
находится ли имя внутри выданного корня, через `strings.EqualFold` и
`strings.ToLower`. Эти операции используют Unicode-правила Go, а не таблицу
сравнения имён конкретного тома. Например, латинская K и знак Кельвина
U+212A сводятся к одной строчной букве, хотя на проверенном NTFS это два
разных имени каталога.

**Подтверждение выдачи наружу:** в изолированном временном дереве созданы
два разных каталога; их различие подтверждено `os.SameFile == false`.
Файл с дополнительным именем внутри выдачи фактически находился также в
соседнем каталоге. До операции у проверяемого SID не было разрешения на
этот файл. Вызывался публичный `acl.Isolate`, без `--allow-links`.

| Имя соседнего каталога | Результат Isolate | На внешнем файле появился grant |
| --- | --- | --- |
| Обычное отличающееся ASCII-имя | отказ | нет |
| Отличающееся на NTFS имя, которое Unicode fold объединяет с корнем | успех | да |

Измерялся настоящий DACL внешнего файла до и после операции. Файлы вне
временной фикстуры не затрагивались. Полный CLI/logon реальной учётки для
этой формы пути не запускался: подтверждена именно выдача прав на внешний
файловый объект production-функцией.

**Влияние:** защитная проверка внешних hard links разрешает выдачу прав
вне выбранного дерева. Как и исходная hard-link проблема, это требует
существующего второго имени; самостоятельное создание ссылки песочницей
на недоступный ей файл не утверждается. Условие не делает дефект
документированным исключением: здесь не был дан `--allow-links`, а
проверка обязана отказать до изменения прав.

**Дополнительное подтверждение того же класса:** два существующих проекта
с одинаковым последним компонентом и различающимися указанной парой
родительскими каталогами получили от настоящего `sandbox.Name` одинаковое
имя группы. Нормализованные пути при этом различались, и файловая система
считала проекты разными. Это детерминированное совпадение входа хеша, а не
подбор коллизии SHA-256.

Последствие выбора общей песочницы установлено по коду: `build` при
несовпадении пути в комментарии меняет комментарий, затем загружает старый
state по тому же имени и добавляет новую выдачу. Проверки, что загруженный
state относится к тому же файловому каталогу, нет. Отдельного
административного end-to-end создания этой пары песочниц здесь не было;
runtime-подтверждение этой части ограничено самим `sandbox.Name`.

**Регрессия:** существующие тесты внешних hard links, внутренних hard links
и короткого имени проходят. Ни они, ни тесты `sandbox.Name` не проверяют
разные каталоги, которые Unicode folding ошибочно объединяет.

**Исправление:** сравнивать принадлежность дерева и идентичность каталога
по файловой системе, сохраняя границы компонентов. Не заменять ToLower
другим общим Unicode fold. Проверять соответствие загруженного state
запрошенному каталогу до повторного использования учётки или смены
комментария. Аналогичные сравнения в pinned/keep-списках и учёте выдач
нуждаются в согласованной проверке. Регрессии должны сначала подтвердить,
что том различает имена, затем проверить отказ выдачи наружу и независимую
идентичность проектов.

## P2-1 — fallback сопоставления имён снова теряет отдельный hard link

Места: `internal/policy/profile/fold.go:158`, `:182`, `:202`,
`internal/policy/profile/record.go:19`, `:34`,
`internal/cli/setup/run.go:192`, `internal/policy/profile/forget.go:109`.

Новая `canonicalEntryPath` правильно различает hard links, когда написание
записи совпадает с хранящимся именем побайтно. Но при отличии регистра она
открывает запрошенное имя, перебирает все записи каталога и берёт первую с
совпавшим `os.SameFile`. Это снова сравнение файлового объекта вместо
конкретного имени. Два разных hard links поэтому могут получить одну
«каноническую» строку.

**Подтверждение:** два временных имени одного файла были переданы
настоящей `DedupeEntries`. С точным написанием результат содержал две
записи — положительный контроль. С написанием обоих имён в верхнем
регистре результат содержал одну. Настоящая `Clear` по этому результату
завершилась успешно, но второе имя осталось с исходным содержимым.

**Влияние:** `.copied` может забыть отдельный путь, и последующий отказ от
копий не удалит его. Это неполная очистка, в том числе копий настроек или
credentials, а не новое доказательство утечки: чтение файлов само по себе
в принятую файловую границу не входит. Та же функция используется
`stillNamed` и `recordVouches`, поэтому чинить только `DedupeEntries`
недостаточно.

**Регрессия:** новый `TestDedupeEntriesKeepsDistinctHardLinkNames` проходит,
но содержит только точные написания. Отдельный тест регистра использует
одно место. Их сочетание не проверяется.

**Исправление:** получить именно имя открытой directory entry либо
отказаться от объединения при неоднозначности. Наличие одинакового file ID
не является достаточным основанием объединить два имени. Нужна регрессия
«два hard links плюс другое написание регистра», включая последующую
очистку обоих путей; сохранить имеющиеся проверки Unicode и обычных
регистровых вариантов.

**Влияние:** пользователь может выбрать и оценить защитный инструмент по
неверному описанию границы. Сам механизм от этой строки не меняется.

**Исправление:** синхронизировать краткие описания npm/Scoop с принятой

## P — проверенные исправления, ограничения и пределы проверки

- Исправление дополнительного `OWNER RIGHTS` grant присутствует в
  `capPresent`; соответствующий тест включён в успешный CI. Локально этот
  существующий тест пропущен по отказу `normalizeOwner`, поэтому локальный
  PASS ему не приписывается. Новый диагностический тест P0-1 проверял
  фактического владельца и выполнился без пропуска.
- Исправление partial-deny в audit подтверждено кодом и локальным PASS
  `TestEveryoneWritableSeesWriteBesideAPartialDeleteDeny`.
- Семь непосредственно связанных существующих регрессий прошли локально;
  одна owner-regression пропущена по причине выше. Полный suite повторно
  не запускался: для него проверен успешный CI того же SHA.
- Четыре новых диагностических измерения выполнены на временных объектах:
  owner-cap fast path, hard-link containment, идентичность проектов и
  hard-link bookkeeping. Измерения не устанавливались как постоянные
  регрессии и удалены из worktree перед отчётным коммитом. Требуемые
  постоянные тесты описаны рядом с находками.
- Документированные Everyone/Users writable вне выдачи, сеть и desktop,
  уже открытые handles, отдельная учётка/DPAPI и необходимость пересоздать
  старые hive не пересчитаны в новые находки. P0 выше нарушают отдельные
  обещания о выдаче и повторном сужении, а не эти принятые ограничения.

**Приёмка релиза:** закрыть обе P0 с отрицательными контрольными случаями,
добавить сочетание hard links и регистра для P2-1, затем получить зелёный
CI нового SHA с обязательными account/boundary-тестами. До этого оснований
объявлять файловую границу готовой к стабильному релизу нет.
