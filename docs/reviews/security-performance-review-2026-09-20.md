# Security and performance review — 2026-09-20 — P0–P3

## Вердикт и границы проверки

**Релиз с текущим `--console-relay` блокируется P0-1.** Новый console host живёт
под неограниченным токеном учётки, но не входит в область действия `Shield`.
В безопасном локальном измерении ограниченный вызывающий процесс получил полный
доступ к такому host и успешно запустил в нём безвредную функцию. Это отдельный
путь исполнения за пределами restricted-token boundary, а не ошибка терминала.

Открытые находки этого отчёта: **P0 — 1, P1 — 0, P2 — 7, P3 — 2**. Одна P1
исходного среза — неработающие standard handles relay-child — вынесена отдельно:
за время ревью появился исправляющий коммит `4fd109a`; повторно считать её новой
открытой находкой было бы неверно. Приёмка этого исправления по CI здесь не заявлена.

Основной срез: `ae06fee363a5c85dac74ba4be5b328aec02e4172`. Изучены история за
13–20 сентября включительно — 319 коммитов, немного шире недельного окна — и
текущие пути account/token/ACL/grants/state/profile/copy/cleanup/launch/stdio,
идентификация путей, блокировки, диагностика и release workflows. Особое внимание
новым relay-коммитам `6dd61ef`, `3a8fd63`, `d9c374c`, `a3cd218`, `33c5f31`,
`ae06fee`, а также оптимизациям bootstrap и исправлениям предыдущих ревью.

Работа выполнена в отдельной worktree. В основном checkout при начале проверки
были незакоммиченные правки `run.go`, `relay_test.go`, `stdin_bridge_test.go`;
они сначала рассматривались только как in-flight. При окончательной сверке
прочитан уже закоммиченный follow-up `4fd109aec87fc15686c793f6dc5ed092037b1755`.
Он меняет standard handles, но не закрывает P0-1 и остальные находки ниже.
Ссылки `файл:строка` относятся к основному срезу, если не указан иной SHA.

Это ревью с ограниченными живыми измерениями, а не доказательство отсутствия
остальных уязвимостей. Полный прогон CI, ARM64, все версии Windows и полный
adversarial e2e под отдельной учёткой в этом ходе не выполнялись. Для обычного
pipe-режима не найден новый подтверждённый файловый обход, независимый от
console-host вопроса; это не сертификат его безопасности. До проверки всех
unrestricted вспомогательных процессов рекомендовать продукт как готовую
границу против враждебного кода нельзя. Для доверенного инструмента, от случайных
ошибок которого нужна дополнительная защита, модель остаётся полезной в рамках
опубликованных ограничений.

## P0-1 — ConPTY оставляет доступный unrestricted conhost за пределами Shield

**Доказательство.** `internal/sandbox/exec/stub.go:178` вызывает
`takeConsoleRelay` до `proc.Shield`. В `internal/sandbox/exec/console.go:188`
`CreatePseudoConsole` вызывается в контексте обычного токена stub. Сам
`token.AsSandbox` возвращает отдельный токен для будущего ребёнка и не меняет
primary token stub. `internal/win/proc/shield.go:119` защищает только текущий
процесс, default DACL его токена и его потоки; перечисление потоков на строке
225 фильтрует их по PID текущего процесса. Уже созданный conhost сюда не попадает.

Результат двух небольших in-memory probes на Windows `10.0.19045.0`:

```text
caller IsTokenRestricted=True
conhost ALL_ACCESS=True
conhost IsTokenRestricted=False
CreateRemoteThread(GetCurrentProcessId)=True
remote returned target pid=True
```

Порядок измерения: создать собственный временный ConPTY обычным токеном;
получить fully restricted token с `DISABLE_MAX_PRIVILEGE` и собственным SID
в restricting list; выполнять открытия под этим restricted thread token;
открыть только созданный этим probe conhost; проверить его token; создать поток,
вызывающий исключительно `GetCurrentProcessId`, и дождаться правильного результата.
В другом измерении также разрешены `TOKEN_QUERY|TOKEN_DUPLICATE|TOKEN_IMPERSONATE`.
Никакие файлы жертвы, чужие процессы или ACL не изменялись; созданный ConPTY закрыт.

Это измерение **same-account механизма**, не готовый полный exploit через
production CLI. Но проверяемое условие production совпадает: `AsSandbox`
оставляет SID своей учётки в restricting list, и именно он разрешает доступ к
процессу того же владельца. У probe этот список даже уже: дополнительные
production SID для разрешающего DACL не нужны. Измерение не опирается на спорное
утверждение, что украденный token удастся impersonate с нужным уровнем: исполнение
в unrestricted адресном пространстве уже подтверждено отдельным потоком.
Семантика прав и исполнения соответствует документации
[CreateRemoteThread](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createremotethread).

**Влияние.** Недоверенная программа получает путь к исполнению как обычная
учётка песочницы без второго access check. Это не превращает её в оператора или
SYSTEM, но возвращает права через `Authenticated Users`, `INTERACTIVE` и другие
SID обычной учётки, которых restricted token намеренно не допускает. Возможна
запись/удаление вне выданных деревьев, в том числе там, где обещание и `--audit`
не описывают исключение Everyone/Users. Lease и job не лечат это: оба процесса
живут одновременно внутри одного разрешённого запуска. Job ограничивает время
жизни, а не права выполняемого кода.

**Рекомендация.** До решения отключить небезопасный relay-путь для релиза либо
сделать его fail-closed. Проверить запуск console host сразу с нужным restricted
primary token. Если API/совместимость этого не позволяют, нужен отдельный
доверенный helper либо защита самого host: process, existing/future threads,
owner-rights и доступные handles, до запуска недоверенного ребёнка. Одной DACL
на процесс недостаточно — прошлые исправления stub уже показали почему.
Нельзя считать сам факт создания ConPTY до Shield безопасным bootstrap-шагом.

**Тест закрытия.** Через реальную цепочку account → stub → restricted program
найти все вспомогательные процессы своего запуска и проверить не только stub:
`VM_WRITE`, `VM_OPERATION`, `CREATE_THREAD`, `DUP_HANDLE`, `WRITE_DAC`, thread
context и token access. Для доступного объекта недостаточно проверить только
`IsTokenRestricted`: нужен контроль реального файлового запрета. Контрольный
каталог вне гранта, разрешённый `Authenticated Users`, должен оставаться
неизменённым, а программа — оставаться работоспособной. Включить вариант без
relay и `--own-console`: их автоматически создаваемые host-процессы в этом
измерении отдельно не проверялись. Существующий тест щита, нацеленный только
на PID stub, этого регресса не обнаружит.

## P1 исходного среза — standard handles relay-child; исправление уже появилось

В `ae06fee`, `internal/win/proc/run.go:149`, `RunWithConsole` использует
`bInheritHandles=false`, но не задаёт `STARTF_USESTDHANDLES`. Числовые значения
родительских standard handles могут остаться у ребёнка без соответствующих
объектов в его handle table. Открытие `CONIN$`/`CONOUT$` вручную успешно, но
это не доказывает работоспособность обычного stdin/stdout программы.
Именно этот обход использовали несколько исходных probes.

Первоначальный незакоммиченный вариант с `CREATE_NO_WINDOW` не принят как
исправление: рабочая консоль могла оказаться другой, а не relay-консолью.
Коммит `4fd109a` задаёт `STARTF_USESTDHANDLES` с тремя нулевыми handles и
добавляет `TestRunWithConsoleGivesTheChildAWorkingGetStdHandle`; он прочитан
отдельно и устраняет исходную ошибку по форме вызова. **В открытый счётчик P1
это не включено.** Результат нового теста и account-crossing CI на этом SHA
в данном ревью самостоятельно не подтверждался.

Приёмка должна одновременно проверять рабочие `GetStdHandle`, ввод и вывод
именно через заданный ConPTY, без `> CON` и без тестового исправления handles
в ребёнке. Иначе тест может измерить другую консоль и снова дать ложный успех.

## P2-1 — завершение relay не дожидается доставки последних байтов

**Доказательство.** `internal/sandbox/exec/console.go:266` запускает `io.Copy`
в goroutine, но не возвращает completion/error. После завершения программы
`stub.go:246` ждёт фиксированные 250 мс, вызывает `relay.close`, затем
`os.Exit`. `console.go:244` закрывает output-read handle сразу после
`ClosePseudoConsole`, не дожидаясь окончания output pump. Байт может ещё
находиться в pipe либо в буфере `io.Copy`, чей `Write` в parent пока заблокирован.
Существующий маленький echo-test не моделирует медленного потребителя и
проверяет наличие маркера, а не полноту потока.

**Влияние.** При backpressure/задержке планирования вывод может обрезаться
при успешном exit code. Любая фиксированная пауза лишь сдвигает это условие.
На Windows 11 24H2 и новее `ClosePseudoConsole` дополнительно возвращается
сразу; официальный критерий завершения вывода — чтение до закрытия pipe,
а не возврат API: [ClosePseudoConsole](https://learn.microsoft.com/en-us/windows/console/closepseudoconsole).

**Рекомендация.** Сделать output pump частью жизненного цикла: остановить
новый ввод, закрыть ConPTY, продолжая drain на отдельной goroutine, дождаться
EOF и завершения записи в parent, затем закрыть read-end и выйти. Ошибку
доставки не превращать молча в успех. Сохранить уже исправленный порядок
job-before-bridge в наружном процессе.

**Тест.** Детерминированный writer-barrier после первого Write: ребёнок уже
закончил, consumer ещё удерживает поток; run не должен успешно завершиться
до release барьера. После release проверить весь ожидаемый вывод. Отдельно
проверить close/error потребителя и поддерживаемые поколения Windows.
Находка подтверждена чтением lifecycle; потери байтов живьём здесь не измерялись.

## P2-2 — ошибка перечисления hard links принимается за полный список

**Доказательство.** `internal/win/pathid/pathid.go:154` и
`internal/win/acl/links.go:178` на любом нулевом результате
`FindNextFileNameW` возвращают накопленные имена с `nil` error. LastError
игнорируется. API отличает конец списка `ERROR_HANDLE_EOF` от ошибки, включая
`ERROR_MORE_DATA`: [FindNextFileNameW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-findnextfilenamew).

**Влияние.** Если перечисление оборвётся после внутреннего имени, до внешнего,
`OutsideNames`/`insideOnly` могут подтвердить безопасность неполного набора.
Следующая запись ACL или `O_TRUNC` затронет тот же file object с внешним именем.
Обычный успешный проход существующих hard-link тестов эту ветку не покрывает.
Это fail-open в error path; управляемый песочницей способ вызвать такую ошибку
на обычном локальном NTFS в данном ревью не доказан, поэтому не P0.

**Рекомендация.** Успешно завершать только на `ERROR_HANDLE_EOF`; остальные
ошибки передавать вызывающему коду. Для `ERROR_MORE_DATA` можно увеличить
буфер и повторить, либо безопасно отказать. Объединить два одинаковых
enumerator, чтобы исправление и тесты нельзя было применить лишь к одному.

**Тест.** Подменяемый enumerator: первое имя внутри, следующий вызов — ошибка,
а не EOF. И grant, и profile overwrite должны отказать до ACL mutation/truncate;
контроль с настоящим EOF должен разрешить внутренние ссылки. Подтверждено кодом
и API-контрактом; инъекция ошибок в этом ходе не выполнялась.

## P2-3 — Prune повторяет разрешение путей и поиск учётки на каждом объекте

**Доказательство.** `internal/policy/grant/prune.go:51` вычисляет
`pathKey(name)` и `pathKey(path)` для каждого объекта, на строке 53 повторно
вычисляет ключ name. Далее `StripOwn` (`internal/win/acl/sweep.go:523`) каждый
раз вызывает `sandboxIdentities`: SID → имя → `NetLocalGroupGetMembers` →
SID членов. Это инвариант всего прохода, а не свойство отдельного файла.
`sid.Parse` (`internal/win/sid/parse.go:15`) не освобождает native SID;
`acl.pin` (`owner.go:190`) добавляет копии member SID в process-global slice
и никогда их не убирает.

**Влияние.** Отзыв по N файлам делает O(N) повторных SAM/LSA операций и
удерживает O(N) экземпляров одних и тех же SID до выхода процесса. Вместе
с P2-4 это существенная лишняя цена `--revoke`/`--rm` на большом дереве,
даже когда менять большую часть ACL не требуется. Это не вечный leak между
отдельными CLI-запусками, но память и задержка растут внутри одного прохода.

**Рекомендация.** Подготовить root key, keep keys и владение SID один раз
под lock, передать immutable operation context во внутренний `stripOwn`.
На объект вычислять ключ один раз. Хранить Go SID buffers в этом context
с явным временем жизни, native allocations освобождать после прохода.
Не добавлять глобальный кэш membership: устаревший состав группы меняет
безопасностное решение. Удалять весь Prune без доказательства эквивалентности
тоже нельзя — он обслуживает реальные исторические границы вложенных grants.

**Тест.** Счётчики resolver/member lookup на небольшом дереве: membership
O(1) на операцию, root key O(1), leaf key O(N). Сохранить проверки account
ACE, owner cap, inherited revoke и вложенных grants. Фактическое ускорение
на большом дереве пока не измерено.

## P2-4 — Canonical выделяет 64 КиБ heap на каждое разрешение пути

**Доказательство.** `internal/win/pathid/pathid.go:45` создаёт
`make([]uint16, syscall.MAX_LONG_PATH)` — 32768 элементов, 65536 байт.
Escape analysis Go 1.26.0 windows/amd64 подтвердил:

```text
pathid.go:45:16: make([]uint16, 32768) escapes to heap in Canonical
pathid.go:45:16: ... (//go:uintptrescapes) ...
pathid.go:140:16: make([]uint16, 32768) escapes to heap in Names
```

**Влияние.** Один вызов на каждый из 150 тысяч файлов — около 9.2 GiB
суммарных transient allocations, до строк, ACL и повторных разрешений.
Это расчёт по коду, **не измеренный RSS и не утверждение, что каждый обычный
старт делает такой обход**. Особенно дороги pinned preflight, Prune и
повторные identity comparisons. Параллельные workers не убирают этот объём.

**Рекомендация.** Малый начальный буфер с ростом по требуемой длине; либо
буфер, принадлежащий worker/операции и повторно используемый после возврата
WinAPI. Сначала убрать повторные вызовы по P2-3/P2-5. Максимальная длина пути,
UNC, short names, Unicode и fail-closed семантика должны сохраниться.
Один общий mutable buffer для параллельных вызовов недопустим.

**Тест.** `AllocsPerRun`/`benchmem` для короткого и длинного пути, повторных
canonicalizations и hard-link enumeration, плюс существующие Unicode/alias
регрессии. Не заменять реальную identity строковым EqualFold ради скорости.

## P2-5 — DedupeEntries делает квадратичные обходы одних и тех же каталогов

**Доказательство.** `internal/policy/profile/record.go:32` сравнивает каждую
entry со всеми ранее сохранёнными. Для разных написаний `sameEntryPlace`
(`fold.go:149`) дважды вызывает `canonicalEntryPath`; тот на каждом компоненте
заново открывает каталог и читает всех детей через `ReadDir(-1)` (`fold.go:173`).
При несовпадении точного spelling добавляются открытия sibling entries.
Похожие попарные проверки есть в `stillNamed` и `recordVouches`.

**Влияние.** Для E entries глубины D и B детей в просмотренных каталогах
обычная форма — O(E²·D·B) работы/созданных directory-entry объектов,
ещё до дорогой ветки aliases. Уже существующий неизменный профиль платит это
после копирования; fingerprint skip не помогает этому слою. Увеличение числа
правил делает warm startup хуже даже без копирования новых байтов.

**Рекомендация.** В рамках одной операции и удерживаемого lease один раз
получать canonical directory-entry identity каждой entry, индексировать map.
Получать финальное имя по уже открытому rooted handle либо переиспользовать
снимки каталогов; сохранять точное различие hard-link names и файлов,
различаемых томом. Отдельно сохранить поведение missing/unresolvable entries.
Ожидаемая структурная цель — O(E·D·B) с прежним resolver либо O(E) разрешений
через handle, не обещание конкретного ускорения без замера.

**Тест.** Счётчик открытий/ReadDir, показывающий однократное разрешение entry,
и прежние тесты Unicode, case/8.3 aliases, двух имён одного hard link,
исчезнувшего source и record ownership. Кэш между запусками здесь небезопасен.

## P2-6 — sweep имеет неограниченный reorder buffer и O(N·P) skip-проверки

**Доказательство.** `internal/win/acl/sweep.go:146` хранит результаты в
`pending`, пока не придёт `next`. Каналы ограничены, но writer продолжает
считывать результаты более поздних задач: если один ранний read задержался,
остальные workers могут пройти всё дерево, а map — собрать O(N) результатов
со строками путей. Размер channels не ограничивает число выданных задач
относительно последнего опубликованного seq. Далее `underSkipped` на строке
193 для каждого результата перебирает все P ранее пропущенных roots.

**Влияние.** Долгий metadata read одного файла может превратить bounded-worker
обход в O(N) retained-memory. При множестве pinned roots skip-часть растёт
до O(N·P). Потомки пропущенного root всё равно классифицируются workers,
хотя последовательный `SkipDir` вовсе не читал бы их на этом проходе.
Это статически подтверждённые пределы; нагрузочный стресс не запускался.

**Рекомендация.** Ограничить число dispatch-задач впереди committed `next`
кредитами, возвращаемыми только ordered writer, либо обрабатывать небольшие
упорядоченные batches. Для depth-first порядка хранить активный skipped root
и сбрасывать его после выхода из поддерева вместо линейного поиска по всей
истории; сохранить точные component boundaries без Unicode folding.
Сохранить preflight-before-mutation и reread перед реальным ACL publish.

**Тест.** Искусственный управляемый barrier на seq 0 при небольшом конечном
списке: число начавшихся задач и размер pending не превышают заданного окна.
Отдельно несколько pinned subtrees, Unicode-соседи, parent-before-child,
ошибка worker и отмена без зависших goroutine. Это unit-тест порядка, а не
требование грузить машину сотнями тысяч фиктивных файлов.

## P2-7 — tree locks не объединяют разные drive aliases одного дерева

**Доказательство.** `internal/base/lock/forpath.go:21` хэширует
`strings.ToLower(filepath.Clean(path))`. `takeTree` (`tree.go:47`) получает
ancestors также из строкового пути. `paths.Normalize` разворачивает symlinks,
но не гарантирует канонизацию SUBST/mapped-drive aliases. Сам проект уже
признал это различие и исправил `state.inside` через `pathid`; lock layer
продолжает использовать другую модель тождества.

**Влияние.** Две команды одного оператора, называющие один каталог реальным
drive path и SUBST-алиасом, могут взять непересекающиеся lock-файлы и параллельно
читать/писать его ACL. Возможны lost updates и расхождение record/ACL.
Это не только уже документированный случай двух разных операторов.
Новая эскалация прав на этой гонке в данном ревью не воспроизводилась.

**Рекомендация.** Перед построением lock hierarchy один раз разрешать root
в канонический путь реального дерева, затем строить его ancestors. Ошибка
идентификации существующего root должна отказать, а не дать независимый lock.
Согласовать нормализацию с grants/pathid и сохранить фиксированный порядок
взятия locks, чтобы исправление не внесло deadlock.

**Тест.** Реальный путь и временный SUBST-алиас: exclusive outer grant
удерживает второй overlapping grant; непересекающиеся siblings продолжают
работать параллельно. Alias должен создаваться только тестом и сниматься
только им; в этом ревью mapping машины не изменялся.

## P3-1 — cleanup сканирует весь профиль даже для узкой маски

**Доказательство.** `internal/policy/profile/cleanup.go:85` рекурсивно обходит
все обычные каталоги, если список cleanup непустой. Проверяется совпадение
конкретного ребёнка, но не возможность совпадения любого будущего потомка.
Например, правило, ограниченное одной cache-папкой и глубиной, всё равно
перечисляет несвязанные histories/logs других программ в профиле.

**Влияние.** Warm startup имеет O(Nprofile·M) mask-проверок и O(Nprofile)
metadata work для M cleanup-масок, хотя нужное поддерево намного меньше.
Ограничение копирования 64 МБ не ограничивает размер файлов, которые сама
песочница создала в своём профиле.

**Рекомендация.** Добавить консервативное `mayMatchDescendant`: literal prefixes
и максимальная допустимая глубина позволяют безопасно не заходить в заведомо
нерелевантные ветки. Для неоднозначных glob оставлять полный обход. Не менять
семантику exclusions/reserved names и не следовать reparse points.

**Тест.** Счётчик посещений на небольшом дереве плюс сравнение результатов
старого и нового matcher для `**`, depth, exclusions и hive-related names.

## P3-2 — command_launch измеряет весь runtime, скрывая настоящую задержку старта

**Доказательство.** `internal/sandbox/exec/run.go:40` открывает фазу
`command_launch` вокруг блокирующего `proc.Run`/`RunAsAccountWithLease`, которые
возвращаются лишь после выхода ребёнка и teardown. Рабочая длительная программа
порождает длинную launch-фазу; отсутствие stdout по такому trace невозможно
отличить от медленного bootstrap. Именно такой неоднозначный trace был
приведён пользователем в обсуждении.

**Влияние.** Профилирование направляет расследование на ACL/создание песочницы,
когда ребёнок уже работает или проблема находится в stdio. Это также мешает
проверять реальные улучшения startup latency.

**Рекомендация.** Разделить `process_create`, `stub_ready`/`program_resumed`,
`program_wait` и `stdio_drain`. `command_launch` либо завершать на фактическом
старте, либо переименовать в `command_lifetime`. События разных процессов
снабдить PID и общим run identifier; отсутствие возможности записать trace
отражать диагностически, без раскрытия credential data.

**Тест.** Ребёнок, управляемо ожидающий тестовый сигнал: launch event уже
завершён, lifetime ещё открыт; после освобождения ожидается отдельный drain/end.

## Что исправления недели действительно улучшили

По коду проверены не только новые кандидаты, но и ранее найденные пути:

- Fully restricted token сохранён: DELETE и FILE_DELETE_CHILD не вынесены
  обратно из второй проверки посредством WRITE_RESTRICTED.
- Account SID включён в модель owner cap/revoke, а точные записи на уже capped
  объектах не принимаются лишь по наличию маркера. `FinishPending`, narrowing
  и `--rm` доходят до Prune; исключение защищённых user-owned файлов сохранено.
- Profile MakeProfile выполняет hard-link preflight до `ProtectFull`, а
  overwrite проверяет destination links отдельно от `os.Root` containment.
  Reparse-point и external-hard-link guard обслуживают разные угрозы.
- Lease перед fillProfile и перед рождением stub, handoff с урезанными правами
  и owner-only slot ACL устраняют несколько прежних concurrency/handle путей.
  Однако lease не защищает unrestricted helper от своего же текущего ребёнка.
- Внешний job закрывается до drain выходных bridge pipes: прежний teardown
  deadlock по оставшемуся фоновому потомку устранён по структуре вызовов.
- Reserved profile names теперь проверяются с учётом неоднозначных Windows
  написаний; неизвестные ключи rules больше не должны молча теряться при Save.
  `--rm` получает разрешённый dir, а release использует `go-version-file`.

Эти изменения не основание снова объявить все прошлые проблемы открытыми.
При этом комментарии «проверено измерением» не заменяют проверку новой цепочки:
история с conhost и standard handles показывает, что добавленный объект или
иной способ открытия может находиться вне того, что измерял старый тест.

## Безопасный порядок оптимизации

Сначала P0-1 и полнота stdio lifecycle. Затем P2-3/P2-4: они убирают повторные
системные вызовы и heap pressure, не ослабляя ACL-проверку. Следом P2-5/P2-6,
после них P3-1. У каждого шага нужны call/allocation counters и сохранение
старых boundary-regressions; конкретные обещания ускорения без профиля не даны.

Для первого grant произвольного уже существующего дерева нижняя граница остаётся
Ω(N): в любом непросмотренном файле может находиться внешний hard link, особый
ACL или sandbox ownership. Наследование NTFS не делает проверку существующих
объектов O(1). Ускорять нужно число проходов/открытий, аллокации и селективность
проверок, а не исключать `target`, `node_modules` или profile scans из гарантии.
Для warm startup цель другая: не платить за всё дерево проекта, а только за
реально затронутые правила/профиль и нужные проверки жизненного цикла.

Первый прогон подтвердил работоспособность выбранных существующих relay-тестов,

Остаются опубликованные ограничения: общедоступные Everyone/Users writable

программой вторую проверку, а не использует обещанное исключение.

boundary regression, приёмка `4fd109a` через account chain и исправление relay

fail-closed гарантии. Остальные пункты можно исправлять последовательно, не
возвращая опасные упрощения механизма. Production-код этим ревью не изменён;
единственный сохраняемый результат — данный отчёт.
