# Security and performance review — 2026-09-22 — round 2 — P0–P3

## Вердикт и область проверки

**Срез пока не готов к безоговорочному релизу.** Подтверждённого нового побега P0
в этом раунде не найдено. Прежняя открытая дверь в unrestricted conhost закрывается
новым кодом и проходит локальную проверку обычного пользователя. Однако в relay
остались два дефекта управления временем жизни, а проверка безопасности console
host допускает недоказанный успех в отдельных ветках. Их следует закрыть до релиза.

Открытые пункты этого отчёта: **P0 — 0; P1 — 2; P2 — 5; P3 — 3.** P0 = обход
заявленной файловой границы; P1 = существенная поломка запуска/завершения или опасная
ошибка времени жизни; P2 = ошибка диагностики, покрытия или заметная проблема
производительности; P3 = менее срочное улучшение. Потенциальный последствиями P0
error path без доказанного способа эксплуатации не посчитан подтверждённым побегом.

Проверен `a0b472276a195792af18de1d1e01132223a62e0e`. Просмотрена история за
15–21 сентября включительно — 238 коммитов, семидневное календарное окно перед
датой отчёта. Отдельно разобраны изменения после предыдущего
[отчёта](security-performance-review-2026-09-20.md), текущие цепочки
account → stub → restricted program, Shield, conhost, jobs/lease, stdio,
ACL/grant/revoke, hard links, profile copy/cleanup, идентичность путей и CI/release.
Ревью истории не означает отдельного полного аудита каждого промежуточного SHA.
Все ссылки `файл:строка` ниже относятся к проверенному срезу.

Работа выполнена в отдельной worktree. Изменён только этот отчёт. Выполнены
небольшие адресные тесты и compiler escape analysis; полный suite, нагрузочные
эксперименты, административные account e2e и тесты с видимым окном не запускались.
Пользовательские проекты, учётки и ACL вне тестовых временных объектов не менялись.

Для доверенных инструментов обычный pipe-режим остаётся полезной дополнительной
защитой от случайной порчи файлов. Рекомендация не распространяется на обещание
изоляции произвольного враждебного кода без перечисленных ниже условий приёмки.
Документированные Everyone/Users, сеть, clipboard, доступное чтение и уже открытые
file handles остаются прежними границами модели, а не новыми находками.

## P1-1 — drain timeout начинается после операции, которая может зависнуть навсегда

**Evidence.** `internal/sandbox/exec/console.go:524`: `finish` сначала закрывает
input и синхронно вызывает `relay.closeConsole()`, а таймер создаёт только на
строке 532. `closeConsole` на строке 418 вызывает `ClosePseudoConsole` на том же
потоке. Output goroutine тем временем может стоять в `Write` потребителю либо уже
закончить `io.Copy` с ошибкой, оставив output pipe открытым и больше не читаемым.

До Windows 11 24H2 `ClosePseudoConsole` может не вернуться, если output pipe не
дренируется. Это прямо описано в [контракте Microsoft](https://learn.microsoft.com/en-us/windows/console/closepseudoconsole).
Следовательно, пятисекундный `relayDrainCeiling` не ограничивает такой teardown:
его ещё не начали отсчитывать. Ошибка consumer, которую новый код теперь хранит,
также может не дойти до возврата из `finish`.

**Impact / confidence.** P1: `wuserbox --console-relay` может остаться ждать после
завершения программы, удерживая slot; новые запуски этой песочницы будут отказаны.
Высокая уверенность в дефекте порядка по коду и API-контракту. Конкретное зависание
с заполненными pipe-буферами в этом ходе намеренно не провоцировалось.

**Recommendation.** Deadline должен охватывать закрытие console и drain вместе.
У close должен быть один владелец и отдельное completion-событие; output pump
нужно сохранять работающим до EOF либо явно обрабатывать отказ получателя так,
чтобы conhost не остался навсегда с открытым нечитаемым pipe. На timeout исключить
повторный блокирующий close из defer и вернуть ненулевой результат без скрытой
потери вывода. Простого переноса `time.NewTimer` выше недостаточно, если основной
поток по-прежнему синхронно ждёт WinAPI.

**Tests.** Три новых drain-теста здесь PASS, но их relay имеет `hpc == 0`, поэтому
эта часть пути не исполняется. Live-тест `console_test.go:819` использует маленький
маркер и отпускает writer-barrier через 300 мс; заполненный output и сломанный
получатель до возврата close там не проверяются. Нужен управляемый close-barrier
в unit-тесте всего teardown и адресный live-тест с небольшим ограниченным объёмом
вывода на поддерживаемой Windows до 24H2. Бессрочный нагрузочный прогон не нужен.

## P1-2 — resize может обратиться к уже освобождённому HPCON

**Evidence.** `internal/sandbox/exec/console.go:578` запускает независимую
goroutine `pumpRelayResizes`; она вызывает `resize` на строке 550. `resize`
проверяет `r.hpc` и передаёт его `ResizePseudoConsole` без синхронизации.
Одновременно главный путь вызывает `closeConsole` на строке 418: освобождает
console и затем записывает `r.hpc = 0`. Остановки или join resize-pump перед
закрытием нет. Наружный отправитель продолжает сообщения до смерти stub, включая
периодический reassert размера без действий пользователя.

Возможный порядок: resize прочитал ненулевой HPCON → close освободил console →
resize передал старое значение в WinAPI. Даже перенос присваивания нуля перед
close оставит гонку между проверкой и использованием. Кроме Go data race, здесь
есть native lifetime: API требует активный HPCON; в открытой
[реализации Microsoft](https://github.com/microsoft/terminal/blob/main/src/winconpty/winconpty.cpp)
HPCON обозначает выделенный `PseudoConsole`, resize читает его поле, а close
освобождает память. Это иллюстрация механизма, не утверждение, что загруженная
на этой машине kernelbase побайтово совпадает с веткой main репозитория Terminal.

**Impact / confidence.** P1: недопустимое использование native ресурса в
unrestricted stub, возможный crash/неверная работа с handle при завершении.
Гонка подтверждена структурой владения; runtime crash и превращение её в побег
не воспроизводились, поэтому P0 здесь не заявляется.

**Recommendation.** Ввести единое синхронизированное владение HPCON. Завершение
должно прекратить новые resize, дождаться уже вошедшего вызова и только затем
освободить ресурс. Mutex с атомарным переводом состояния в closed под ним либо
один управляющий worker годятся; простой atomic load/store самого числа не
защищает native вызов от concurrent free. Согласовать решение с P1-1, чтобы
ожидание блокирующего WinAPI не сделало новый deadlock.

**Tests.** Детерминированно удержать resize между получением handle и WinAPI,
начать finish, проверить порядок и однократное освобождение. После closed resize
должен быть no-op. Запустить этот адресный тест под race detector. Существующий
resize-тест проверяет получение размера ребёнком до выхода; такую границу
завершения он не фиксирует. Crash-probe в этом ревью не запускался.

## P2-1 — ошибка GetConsoleProcessList превращается в разрешение пропустить Shield

**Evidence.** `internal/sandbox/exec/console.go:134` отбрасывает LastError и
возвращает `nil` при любом `n != 1`. Включая `n == 0`, которое по
[GetConsoleProcessList](https://learn.microsoft.com/en-us/windows/console/getconsoleprocesslist)
означает не успешный пустой список, а неудачу API. Отсутствие консоли и отказ
узнать её состояние стали одним результатом. В production этот код стоит перед
Shield и запуском недоверенного ребёнка.

**Impact / confidence.** Подтверждённый fail-open error path: при непредвиденной
ошибке проверки birth host может остаться незакрытым, а запуск продолжится.
Повторение прежнего P0 при управляемом возникновении ошибки возможно по механизму,
но способ вызвать её из sandbox на обычной Windows здесь не установлен. Поэтому
это P2, а не утверждение о готовом новом exploit.

**Recommendation.** Различать явно подтверждённый запуск без собственной консоли
и неизвестное состояние. Production account-stub приходит по известному пути
`CREATE_NO_WINDOW`; общий helper не должен снимать обязательную проверку только
потому, что его используют unit subprocess с другой консолью. Неожиданную ошибку
API возвращать, перечисление hosts и приёмку выполнять до запуска ребёнка.

**Tests.** Инъекция ошибки получения списка должна остановить реальный bootstrap
до `Run`; отдельные положительные случаи — известная inherited/no-console форма
helper и нормальный birth host. Наличие процесса в happy-path тесте эту ветку
не покрывает. Укрепить данный error path до заявления полной fail-closed гарантии.

## P2-2 — guard после исправления P0 не доказывает защиту всех потоков conhost

**Evidence.** `internal/e2e/conhost_test.go:312` намеренно сохраняет только один
thread ID на процесс. На строке 282 отсутствие этого ID просто отменяет
thread-проверки, но host всё равно получает `measured: true`. Ошибки OpenThread
не различаются: и `ACCESS_DENIED`, и исчезнувший объект считаются закрытой дверью.
Низкоуровневый prowler (`internal/win/proc/prowler_test.go`, `aThreadOf/prowl`)
тоже берёт первый найденный поток. В новом `a0b4722`
(`internal/win/proc/shield.go:322`) отказ `WRITE_DAC` вообще засчитывается как уже
защищённый поток, без отдельного read-back/проверки остальных опасных прав.

**Impact / confidence.** P2 — пробел в обязательном regression oracle, не
доказанный обход текущего DACL. Из теста нельзя вывести, что второй существующий
поток или поток, родившийся после смены default DACL, закрыт. Отказ одного права
сам по себе не означает отказ других: `WRITE_DAC`, `THREAD_SET_CONTEXT` и
impersonation являются разными [правами thread object](https://learn.microsoft.com/en-us/windows/win32/procthread/thread-security-and-access-rights).
Обоснование новой ветки может быть верным для измеренного startup conhost, но
однопоточный oracle его не закрепляет.

**Recommendation.** Проверять все обнаруженные живые потоки host, отдельно
обрабатывать исчезновение и остальные ошибки, требовать непустого измеренного
набора там, где host жив. Добавить контролируемое создание потока после смены
default DACL и чтение/проверку его защиты. Для `ACCESS_DENIED` ветки закрепить
предпосылки отдельным тестом; не считать произвольный отказ доказательством
именно установленного Shield.

**Tests.** Мутация, оставляющая второй поток открытым при закрытом первом, должна
обязательно делать guard красным. Нужны случаи «поток не удалось перечислить»,
«исчез после snapshot» и «появился после установки token default DACL». Длинный
stress не заменяет эти управляемые случаи. Административная e2e здесь не запускалась.

## P2-3 — обычный административный go test всё ещё открывает видимое окно

**Evidence.** `921810c` добавляет opt-in `WUSERBOX_E2E_OWN_CONSOLE` в
`internal/e2e/streams_test.go:118`. Однако новый conhost boundary-test на строке
464 `internal/e2e/conhost_test.go` безусловно добавляет leg `own console` с
`WUSERBOX_OWN_CONSOLE=1`. `takeOwnConsole` вызывает настоящий `AllocConsole`.
Этот тест входит и в обычный `go test ./...`, и в именованный Delete boundary.
Единственный внешний gate — administrator, не согласие показать окно.

**Impact / confidence.** P2: на администраторском рабочем столе возвращается
помеха, которую пользователь просил убрать. Это подтверждается кодом; окно
специально не открывалось. Комментарий CI «единственный тест, который показывает
реальное окно» сейчас неверен.

**Recommendation.** Разделить безоконные host-проверки и own-console leg.
Последний запускать в существующем явно включаемом CI measurement, сохранив
требование PASS/без SKIP именно в этом шаге. Не выключать все проверки P0 ради
тишины и не возвращать AllocConsole → ShowWindow, которое уже успевает мигнуть.

**Tests.** Проверка default selection должна исключать все реальные AllocConsole
legs, а opt-in шаг — выполнять both terminal/host-boundary measurements.

## P2-4 — warm-copy остался квадратичным до оптимизированного dedupe

**Evidence.** `internal/policy/profile/forget.go:24` проходит ранее записанные
entries; `stillNamed` на строке 270 линейно ищет каждую в текущем списке.
Для каждой неравной пары вызывается `sameEntryPlace`, который на
`fold.go:155` создаёт новый resolver и новые directory snapshots. Даже одинаковые
списки длины K оплачивают до `K*(K-1)/2` таких сравнений перед совпадениями по
spelling. `copy.go:340`, `recordVouches`, повторяет эту форму при missing source.
`TestSameEntryPlaceSharesOneLookBetweenItsTwoSpellings` измеряет один resolver
внутри одной пары, а не один resolver на весь `Copy`.

Кроме того, внутри самого нового resolver `fold.go:293` линейно ищет компонент
в cached `[]DirEntry`; alias fallback на строке 313 снова открывает каждого
sibling. Поэтому устранение повторного ReadDir в `DedupeEntries` не делает все
его CPU/syscall операции O(K) при широких каталогах.

**Impact / confidence.** P2: повторный запуск с неизменными файлами всё ещё может
долго проверять профиль. Для K entries глубины D и B соседей сравнение до dedupe
остаётся O(K²·D·B) работы; fingerprint skip этот этап не обходит. Структурная
сложность подтверждена, ускорение в миллисекундах не выдумывается.

**Recommendation.** Передавать один operation resolver и индекс текущих/записанных
entries всему `forget/copy/record` под lease. Для exact spelling индексировать
детей каждого snapshot map, а дорогие alias-ответы кешировать в пределах операции.
Сохранить разные hard-link names, Unicode-имена, которые том различает, и поведение
missing entries. Кэш между запусками здесь не нужен.

**Tests.** Счётчики resolver/Open/ReadDir на маленьком неизменном профиле должны
обрамлять целый `Copy`, а не только `DedupeEntries`. Добавить missing-source и
respelling, сравнить результат со старой семантикой. Уже выполненные Unicode/
hard-link dedupe-тесты PASS, но всей warm-start цены не измеряют.

## P2-5 — audit применяет inherit-only ACE к самому каталогу

**Evidence.** `internal/win/acl/entries.go:226`, `heldBy`, складывает allow/deny
маски без проверки `one.access.inheritance & InheritOnly`. Между тем сам проект
правильно определяет `InheritOnly` в `ace.go:21` как запись, не действующую на
объект. Правила [наследования ACE](https://learn.microsoft.com/en-us/windows/win32/secauthz/ace-inheritance-rules)
различают effective и inherit-only записи.

**Impact / confidence.** P2: возможны обе ошибки `--audit`. Inherit-only allow
даёт ложный writable для родителя. Inherit-only deny всех changing bits вместе
с effective allow даёт ложное «не writable», хотя запись/создание на самом
каталоге разрешены. Это особенно существенно для команды, которая должна
показывать исключения из файловой границы. Подтверждено логикой расчёта и
контрактом флагов; новый живой ACL fixture в этом ходе не создавался.

**Recommendation.** При ответе о самом объекте исключать inherit-only ACE.
Дальнейший расчёт должен уважать effective порядок/семантику ACL; если остаётся
эвристикой, не представлять его полноценным AccessCheck. Дочерние эффективные
унаследованные ACE продолжать учитывать — прежний regression об inheritance
терять нельзя.

**Tests.** Два небольших fixture: только `(OI)(CI)(IO)` allow и effective allow
плюс `(OI)(CI)(IO)` deny. Сравнить audit с реальным открытием объекта под
соответствующим ограниченным токеном. Нужен контроль самого родителя и ребёнка,
на которого запись уже действует.

## P3-1 — bounded reorder не ограничивает память остального ACL обхода

**Evidence.** Когда внутри root есть хотя бы один relevant pinned grant,
`internal/win/acl/sweep.go:357` вызывает `pinned.snapshot` для каждого объекта.
`internal/win/acl/pinned.go:112` сохраняет path → resolved key до конца операции.
Это O(N) строк и map entries независимо от credits. `filepath.WalkDir` также
читает сортируемое содержимое очередного каталога целиком; один широкий каталог
остаётся отдельной O(B) памятью. Старый дефект pending-map при этом исправлен.

**Impact / confidence.** P3: память grant/revoke на большом дереве по-прежнему
может расти пропорционально N при nested grants. Подтверждено структурой хранения;
большой искусственный лес не создавался.

**Recommendation.** В профиле памяти отдельно считать pending, pinned snapshots
и directory listings. Сначала сократить кеш до информации, нужной после изменения
доступности путей; возможность хранить только доказанные pinned matches нужно
проверить с fail-closed обработкой новых/неразрешимых объектов. Не объявлять весь
sweep O(window) и не удалять snapshot вслепую: некоторые пути после изменения ACL
уже нельзя разрешить повторно. Для широких каталогов рассмотреть порционный
directory walker с сохранением parent-before-child и семантики skipped subtree.

**Tests.** Маленький вложенный-grant fixture со счётчиком сохранённых ключей;
проверки pinned aliases/Unicode и отказа повторного открытия после cap. Вводить
потоковый walker только с тестом порядка, а не только с замером скорости.

## P3-2 — трасса по-прежнему путает старт с временем работы программы

**Evidence.** `internal/sandbox/exec/run.go:41` открывает `command_launch` вокруг
блокирующего run целиком. `internal/cli/setup/run.go:72` ждёт slot между prepare
и profile_copy без собственной фазы. Новые ожидания conhost/snapshot/drain внутри
stub также не имеют отдельных startup spans.

**Impact / confidence.** P3, подтверждено кодом: долго работающий агент выглядит
как долгий запуск, а ожидание занятого slot выглядит как необъяснимый разрыв
между фазами. Это уже мешало диагностировать отсутствие stdout в обсуждении.

**Recommendation.** Разделить slot_wait, process_create, host_shield,
program_resumed, program_wait и stdio_drain; command_launch завершать на resume
или назвать command_lifetime. Добавить PID/run identifier для двух процессов.
Не добавлять пароли, credential content и весь environment в trace.

**Tests.** Управляемо ожидающий ребёнок: resume-событие уже есть, runtime-span ещё
открыт; после release появляется отдельный drain. Это прежняя незакрытая находка,
а не новое ухудшение от последней оптимизации.

## P3-3 — audit повторяет ACL чтения и удерживает native SID на каждый объект

**Evidence.** `internal/cli/inspect/audit.go:38` спрашивает Everyone и Users
раздельно; при находке ещё раз вызывает `acl.Unreadable`. Каждый `heldBy`
(`entries.go:226`) повторяет GetNamedSecurityInfo и `sid.Parse`. В
`internal/win/sid/parse.go:17` SID выделен Windows; появившийся `sid.Free` здесь
не вызывается. Go GC этой native памятью не владеет.

**Impact / confidence.** P3: на глубоком audit — два-три чтения одного DACL и
O(N) оставшихся native SID allocations до выхода CLI. Это не вечный leak между
запусками и не прежний уже исправленный SAM lookup на каждый объект Prune.
Подтверждено call graph и отсутствием соответствующего освобождения.

**Recommendation.** Один audit-question на каталог: одно чтение descriptor,
одна обработка ошибки и ответы по обеим identities. Постоянные SID держать
в operation context с явным освобождением после обхода. При исправлении P2-5
это естественно убирает и повторный разбор того же ACL.

**Tests.** Счётчик reads/parse/free на небольшом дереве с обычным и unreadable
объектом; одна неудача не должна превращаться в definitive writable. Native
allocation balance измерять отдельно от Go `AllocsPerRun`.

## Где реально снизить O и аллокации

Первый безопасный grant существующего произвольного дерева имеет нижнюю границу
Ω(N): непроверенный объект может содержать внешнее hard-link имя, отдельный ACL
или sandbox ownership. Пропустить `target`, `node_modules` или любой непроверенный
подкаталог означает изменить гарантию. В этом слое полезны меньше повторных
открытий, освобождение native памяти и ограничение временных буферов.

Для warm-copy снижение порядка реально: общий индекс вместо попарных `stillNamed`
и `recordVouches` убирает K² сравнений; словарь детей snapshot убирает линейный
поиск каждого exact компонента. Это более значимый следующий шаг, чем увеличение
числа ACL workers сверх текущих восьми. Новая selective cleanup уже движется
по этому принципу и сохранена в положительном вердикте предыдущих фиксов.

Compiler escape analysis на Go 1.26.0 подтвердил: `Canonical` и `enumerateNames`
по-прежнему отправляют начальные `make([]uint16, 256)` в heap. Это **512 байт**
на буфер вместо прежних 64 КиБ, поэтому первый выигрыш реален; обещать zero-alloc
путь пока нельзя. Объявление локального `[256]uint16` само по себе не доказывает
stack placement: указатель проходит через заменяемые function variables/WinAPI.
Следующий безопасный вариант — bounded scratch buffer на worker/operation,
отдельный рост для длинного имени и проверка lifetime/KeepAlive. Глобальный один
буфер сломает параллельные разрешения. Значение оптимизации надо сверять с I/O
ценой, не считать каждый допустимый heap escape дефектом.

Новый host shield дополнительно перечисляет системные процессы/потоки при каждом
старте. Это O(P + T), а не размер проекта. Пока нужен надёжный способ назвать
нужные объекты, удалять это измерение ради скорости нельзя. Сначала выделить его
в trace и проверять повторные snapshots только при реальной необходимости.
