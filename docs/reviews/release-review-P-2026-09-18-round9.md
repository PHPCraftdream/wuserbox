Проверен `09369d7453703e7f0c304f5a5e58e5de19f228bd`: исправления после round 8
и основные подсистемы проекта. Приоритет — файловая граница, выдача и отзыв ACL,
копирование профиля, запуск под отдельной учёткой и регрессионное покрытие.

**Вердикт: релиз блокируется. P0 — 2; P1 — 0; P2 — 1; P3 — 0.**

В текущем состоянии нельзя рекомендовать эту сборку как проверенную границу для
недоверенных программ. Обычные сценарии проходят CI, но два измеренных случая
позволяют самому обслуживанию профиля изменить объект вне профиля. Это дефекты
обработки заранее существующего состояния ссылок, а не доказательство того, что
песочница сама может создать ссылку на любой недоступный ей файл.

Production-код не изменён. В коммит входит только этот defensive report.

## P0-1 — проверка ссылок при init выполняется после выдачи прав внешнему объекту

**Место:** `internal/sandbox/init.go:375`, `internal/sandbox/init.go:385`,
`internal/account/ownprofile.go:67`.

`ensureProfile` сначала вызывает `MakeProfile`, затем `RegisterProfile`, и только
после этого — `ValidateLinks`. Внутри `MakeProfile` вызов `ProtectFull` записывает
наследуемый Full Control для учётки песочницы. Windows распространяет эти права
на уже существующие наследующие файлы профиля.

Если такой файл имеет второе hard-link имя вне профиля, обновляется единый ACL
файлового объекта. Поэтому внешний файл уже получает права учётки до того, как
новый скан обнаруживает его второе имя и возвращает ошибку. Отказ не отменяет
произошедшее расширение доступа. Учётка песочницы присутствует и в обычном, и в
ограничивающем списке её рабочего токена, поэтому выданное ей разрешение нельзя
считать закрытым вторым access check.

**Измерено в этом раунде:** на временном внешнем control-файле до вызова не было
записи для проверяемого SID. После реального `MakeProfile` его DACL содержал новый
наследуемый Full Control для этого SID. Следующий `ValidateLinks(profile, false)`
отказал из-за внешнего имени. Содержимое control-файла для измерения не менялось:
подтверждённым эффектом было изменение его разрешений за пределами профиля.

В качестве различимого principal использовался `BUILTIN\Users` только на
одноразовых тестовых данных. Это измеряет распространение ACL самой функцией,
без создания новых учёток. Полный CLI init с настоящей учёткой заново не
воспроизводился; его порядок вызовов проверен по исходникам. Найденное относится
к выдаче нового права, а не к документированному исключению для каталога, который
изначально был общедоступным.

**Почему P0:** подготовка профиля расширяет запись за заявленную границу и
оставляет расширение даже при отказе init. Возможность оператора создать или
изменить ссылку после предыдущей проверки не делает последующий отказ безопасным.

**Направление исправления:** проверять профиль до любой операции, способной
распространить ACL, включая `ProtectFull`; держать эту проверку внутри пути,
который действительно изменяет разрешения, чтобы другой вызывающий не мог
обойти её. Предусмотреть безопасный отказ при изменении дерева между проверкой
и применением. Одного дополнительного скана после записи недостаточно.

**Критерий закрытия:** повторная подготовка профиля с внешним hard-link именем
отказывает, а DACL и содержимое внешнего объекта остаются прежними. Отдельный
положительный контроль подтверждает, что обычный профиль получает нужные права.
Регрессия должна проходить через реальную подготовку профиля, а не только
вызывать `ValidateLinks` отдельно.

## P0-2 — новый guard копирования пропускает назначение через внутреннюю symlink

**Место:** `internal/policy/profile/mirror.go:265` и
`internal/policy/profile/mirror.go:276`.

Проверка `OutsideNames` выполняется только когда `root.Lstat(dst)` сообщает об
обычном файле. Для symlink эта ветка пропускается. Следующий `root.OpenFile` с
`O_TRUNC` может разрешить относительную ссылку, которая остаётся внутри профиля:
такое разрешение само по себе не нарушает правила `os.Root`.

Однако файловый объект, достигнутый таким разрешением, может иметь hard-link
имя снаружи. В этом случае проверяется тип исходного directory entry, а изменяется
другой, разрешённый через него объект. Его внешние имена новый guard уже не
проверяет. Таким образом, прямое hard-link назначение блокируется, но то же
свойство конечного объекта через разрешённую внутреннюю ссылку остаётся опасным.

**Измерено в этом раунде:** безопасный тест на временных файлах вызвал настоящий
`profile.Copy` с таким назначением. Результат — `error == nil`; внешний control-файл
получил содержимое копируемого источника. Относительная symlink была успешно
создана на этой машине, тест не пропускался. Гонки, изменения production-кода и
снятия защиты в функции для этого измерения не требовалось.

Это уточнение незакрытой части P0 из round 8, а не новое утверждение о возможности
создать произвольный hard link из ограниченной учётки. Происхождение внешнего
hard-link имени в реальной песочнице здесь отдельно не измерялось. Само свойство
копировщика — не изменять внешний файловый объект при допустимом входном
состоянии — опровергнуто прямым вызовом его рабочего кода.

Проверка при `--init` не является проверкой каждого последующего копирования:
обычный запуск существующей песочницы проходит через `prepare` и `fillProfile`,
а новый `ValidateLinks` размещён внутри `ensureProfile` на пути init. Кроме того,
P0-1 показывает, почему текущий порядок самого init нельзя считать достаточным
страхующим механизмом.

**Направление исправления:** связать проверку с тем файловым объектом, который
будет изменён, включая разрешение ссылок, либо публиковать копию новым файловым
объектом внутри закреплённого корня без усечения прежнего. У отдельной проверки
имени перед повторным открытием также остаётся вопрос смены назначения; в этом
раунде конкурентная разновидность не измерялась и отдельной находкой не считается.

**Критерий закрытия:** копирование сохраняет внешний control-файл и его ACL при
прямом и непрямом назначении на общий объект. Допустим явный безопасный отказ.
Обычная копия и согласованная семантика внутренних hard links должны сохраняться.

## P2-1 — новые hard-link регрессии не включены в обязательный boundary gate

**Место:** `.github/workflows/ci.yml:92`,
`internal/policy/profile/mirror_test.go:52`,
`internal/policy/profile/mirror_test.go:77`,
`internal/win/acl/link_test.go:125`.

В именованном списке `Delete boundary` отсутствуют обе новые проверки
`TestCopyRefusesAnExternalHardLinkBeforeTruncatingIt` и
`TestCopyAllowsHardLinksWhoseNamesStayInTheProfile`, а также все три
`TestValidateLinks…`. Они выполняются общим `go test ./...`, однако при
недоступности создания ссылки вызывают `t.Skip`. Общий шаг разрешает пропуски;
только именованный boundary gate превращает такой пропуск в ошибку CI.

**Подтверждение:** список workflow прочитан на проверенном SHA; в логе актуального
boundary шага — 70 PASS и 0 SKIP. Эти 70 не включают перечисленные новые свойства.
Локально все пять новых проверок в этом раунде действительно прошли, так что
находка касается защиты от будущего тихого пропуска, а не ложного заявления,
будто они сейчас падают.

**Исправление:** добавить эти свойства и новые регрессии для P0-1/P0-2 в
обязательный именованный набор; проверять отсутствие пропусков и фактическое
число выполненных тестов. Тест отдельного сканера не заменяет регрессию порядка
всей операции, изменяющей профиль.

## Принятые ограничения — отдельно от находок

Изначально общедоступные writable Everyone/Users-каталоги, отсутствие изоляции
сети и сильной изоляции UI, разрешённое чтение и копии credentials, уже открытые
handles, а также документированная миграция старых hive не пересчитаны в новые
P-находки. Оба P0 относятся к действиям самого обслуживания профиля с правами
оператора и к внешнему объекту, который это обслуживание обязано оставлять
неизменным.

Для повторного release verdict нужны исправления обоих мест и зелёный
обязательный CI с проверками конечного эффекта на внешнем объекте — содержимого
и разрешений, а не только кода возврата сканера.
