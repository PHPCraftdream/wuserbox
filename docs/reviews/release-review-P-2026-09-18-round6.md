## P0-1 — отзыв сохраняет широкую ACE на объекте, принадлежащем песочнице

Места: `internal/win/acl/reclaim.go:106`, `:159`, `:166`, `:172`;
путь вызова — `internal/policy/grant/revoke.go` → `acl.TakeBack`.

`takeBack` удаляет записи, непосредственно называющие SID группы/учётки
песочницы, и устанавливает owner-cap. Но в ветке `holdsOwn` все остальные
неунаследованные ACE переносятся в новую DACL без сужения. Среди них может
быть `Everyone: Full Control`, записанная владельцем файла до отзыва.
Присутствие `OWNER RIGHTS: RX` её не отменяет. В другой ветке достаточным
условием успеха остаётся один `capPresent`, который проверяет только
`OWNER RIGHTS`.

Исправленный в предыдущем раунде `alreadyCapped` вызывается при `Isolate`,
а этот путь отзыва его вообще не использует. Поэтому успешный новый grant
и успешный revoke сейчас обеспечивают разные гарантии.

**Подтверждено измерением на временных файлах.** Фактический владелец каждого
файла прочитан из security descriptor и совпадал с идентичностью, переданной
`TakeBack`. Обе половины вызывали настоящий `TakeBack` и завершились без ошибки:

| После отзыва | Только явная ACE владельца | ACE владельца и Everyone: FC |
| --- | --- | --- |
| OWNER RIGHTS: RX установлен | да | да |
| Windows AccessCheck с fully restricted token разрешает запись | нет | да |
| Новое открытие и запись через `os.WriteFile` | отказ | успех |

До измерения не оставлялись открытые файловые handles. Это сохранение
разрешения на **новое** открытие, а не документированное свойство уже открытых
handles. Ограниченный токен имел отдельный синтетический restricting SID;
положительный результат второй проверки приходил через Everyone.

Полная цепочка двух новых локальных учёток здесь повторно не запускалась.
Измерены production-функция отзыва, реальная DACL, новый файловый доступ и
проверка Windows под fully restricted token; это больше, чем статическая
гипотеза, но не следует называть такой стенд новым real-account e2e.

**Влияние:** объект, который песочница создала и успела перепермиссионить до
отзыва, остаётся изменяемым после успешного revoke. Это выходит за принятую
оговорку о каталогах, которые сама машина уже оставляла общедоступными:
широкая ACE создана внутри выданного дерева, и `docs/limits.md` отдельно
обещает закрыть такое расширение следующим `--revoke`.

**Что исправить:** сформулировать и обеспечить постусловие отзыва по всем
идентичностям, через которые токен может получить изменяющие права, а не
только по имени отзываемой ACE. У объекта владельца-песочницы нельзя считать
произвольные остальные ACE доверенной политикой оператора. Сохранить доступ
оператора и независимые законные выдачи другим песочницам.

**Регрессия:** настоящий revoke через командный путь и real account; файл
создан песочницей, до отзыва на нём появилась широкая ACE. После успеха новые
write/delete/WRITE_DAC должны отказывать. Проверить Everyone и Users,
наследующую и защищённую DACL, с явной ACE учётки и без неё. Контрольная
половина обязана доказать доступность файла до отзыва.

## P0-2 — Unicode исправлен в имени песочницы, но не в выборе правил и отзыве

Места: `internal/policy/config/lookup.go:13`, `:29`;
`internal/policy/state/grants.go:25`, `:140`.
Связанные непереведённые сравнения: `internal/policy/state/repair.go`,
`internal/policy/grant/prune.go`, `internal/win/acl/reclaim.go:60`,
`internal/win/acl/owner.go:317`.

Новая `sandbox.Name` различает NTFS-различные каталоги `K` и `K`, и новый
тест на неё проходит. Однако `config.SamePath` и `State.find` продолжают
применять `strings.EqualFold`. Выбор правил проекта и выбор отзываемой записи
снова считают эти два разных каталога одним.

**Подтверждены два результата на реально созданных каталогах:**

- Windows file identity: каталоги различны; `sandbox.Name`: имена различны.
  В `Config` задано правило только для `K`. Вызов `GrantsFor(K)` возвращает
  RW-выдачу из правила `K`. `grants.FromConfig` без дополнительной проверки
  применяет полученные specs к текущей песочнице. Измерен именно выбор
  правила; полный административный init по этому правилу не запускался.
- Настоящий `State.Ensure(K, RW)` выдал право синтетическому SID. Затем
  `State.Remove(K)` вернул успех, записал пустой список grants, но Windows
  AccessCheck по `K` всё ещё разрешил создание. Метод нашёл запись `K`,
  а `grant.Revoke` применил к аргументу `K`; первая выдача осталась в NTFS
  и исчезла из учёта.

Во второй проверке задействованы настоящие запись state, установка ACL,
отзыв и Windows AccessCheck; это не только сравнение строк. Существовавшие
пользовательские каталоги и настройки не использовались.

**Влияние:** правила могут выдать одной песочнице дополнительные каталоги,
разрешённые другой. Отзыв может сообщить об успехе, сохранив действующее право
и убрав единственную запись, по которой его находили. Оба результата нарушают
границу управления разрешениями.

**Что исправить:** провести идентичность пути через весь жизненный цикл:
config, state, списки сохраняемых поддеревьев, grant/revoke, repair и preview.
Нельзя исправлять только хеш имени или заменять все сравнения на file ID:
для имён hard links объект и запись каталога — разные вопросы, что отдельно
показывает P0-3. Для недоступных/исчезнувших путей нужна определённая политика,
сохраняющая учёт без предположения о Unicode-равенстве.

**Регрессия:** две NTFS-различные Unicode-папки с разными project rules;
выдача, repair, revoke/remove-dir и explain должны продолжать различать их.
После ошибочного имени revoke должен отказывать либо отзывать строго
названную выдачу; ему нельзя удалять запись другой. Отдельно проверить
keep/pinned-исключения при обходе, где ещё осталось Unicode lowercasing.

## P0-3 — выдача отдельного файла обходит запрет внешних hard links

Места: `internal/win/pathid/pathid.go:70`, `:81`;
`internal/win/acl/links.go:76`; `internal/win/acl/sweep.go`, функция `inspect`.
CLI допускает этот вход: `internal/cli/access/target.go` и
`internal/cli/access/grant.go` не требуют, чтобы цель была каталогом.

`Within` начинает с file ID самого проверяемого пути и сразу возвращает true,
если он равен file ID корня. Это пригодно для проверки дерева с каталогом
в корне, но если корень — сам выдаваемый файл, любой его hard link имеет тот
же file ID, в том числе имя в другом каталоге.

`inspect` явно проверяет и корневой файл. Тем не менее после перехода со
строковой проверки на этот `Within` все его другие имена признаются
внутренними. Проверки на hard link внутри выдаваемого **каталога** этого
случая не покрывают.

**Подтверждено:** созданы временный файл и второе имя в другом временном
каталоге. До выдачи Windows AccessCheck под restricted token запрещал запись
через внешнее имя. Настоящий `State.Ensure(имя-файла, RW)` без `--allow-links`
завершился успешно; после него тот же AccessCheck разрешил запись внешнему
имени. DACL принадлежит файлу, поэтому изменилось разрешение обоих имён.

**Влияние:** обычная выдача может открыть файл по имени вне указанной цели,
хотя инструмент обещает обнаруживать эту форму и требовать `--allow-links`.
Это регрессия именно новой проверки containment. Возможность песочницы
самостоятельно создать ссылку на ранее недоступный файл здесь не утверждается:
дефект состоит в административной выдаче, достигающей дальше запроса.

**Что исправить:** либо явно отказаться от выдач отдельных файлов во всех
входах до изменения ACL, если продукт поддерживает только каталоги, либо
проверять их отдельным правилом идентичности directory entry. Равенство
идентификатора файла не доказывает нахождение другого имени внутри цели.

**Регрессия:** настоящая выдача отдельного файла с внешним hard link должна
отказывать до изменения ACL; внешний объект после отказа остаётся
недоступным. Отдельный положительный контроль — осознанный `--allow-links`.
Сохранить существующий контроль, разрешающий ссылки целиком внутри дерева.

## P1-1 — новая схема имени теряет существующие и удалённые проекты

Места: `internal/sandbox/name.go:32`,
`internal/win/pathid/pathid.go:56`, `:58`, `:64`;
`internal/cli/setup/prepare.go:118`, `internal/cli/setup/rm.go:51`.

До изменения имя хешировалось от lowercase нормализованного пути. Теперь
оно хешируется от `entry:` и фактического написания либо от `missing:` и
ASCII-folded пути. Совместимого поиска прежней записи нет.

У этого два наблюдаемых последствия:

- Обновление меняет имя обычного, даже полностью ASCII-проекта. Предыдущие
  group/account/profile/state остаются под старым именем, а текущий lookup
  считает проект новой песочницей. Теряются выбранные только в state выдачи,
  ограничения и настройки; старые ресурсы остаются на машине.
- Даже без обновления удаление/переименование каталога меняет ключ с `entry:`
  на `missing:`. `--rm --dir <старый-путь>` ищет уже другое имя и не удаляет
  созданную ранее песочницу. Это ломает собственный документированный способ
  убрать песочницу исчезнувшего проекта и рекомендацию `facts.ProjectGone`.

**Измерено:** для одной временной ASCII-папки вычислены прежнее имя по
предыдущему алгоритму и текущее имя; затем папка удалена и снова вызвана
настоящая `Name` с тем же абсолютным путём. Получены три разных имени.
Выбор state/removal по производному имени подтверждён кодом. Полный lifecycle
машинной учётки для этого диагностического случая не создавался.

**Что исправить:** добавить безопасное разрешение уже существующей identity
по сохранённой записи/комментарию и явный путь миграции. Существование каталога
не должно быть условием нахождения его учётки для удаления. При неоднозначных
старых Unicode-записях следует отказать, а не молча присоединять другой проект.

**Регрессия:** обновление sandbox, созданного прежней версией, сохраняет его
identity и state-настройки; удаление и переименование проекта не мешают
`--rm` убрать старые account/group/profile/записи и дополнительные grants.

## P2-1 — неоднозначный hard-link lookup теряет запись об уже сделанной копии

Места: `internal/policy/profile/fold.go:146`, `:211`;
`internal/policy/profile/copy.go:294`;
`internal/cli/setup/run.go`, функции `fillProfile` и `union`.

Новый отказ `canonicalEntryPath` при нескольких совпавших file ID исправляет
объединение разных hard-link имён в Dedupe. Но этот же отказ используется в
`recordVouches`. Он возвращает false даже для неизменившегося написания
уже записанного entry, если его регистр отличается от записи на диске и
объект имеет другое hard-link имя.

`forget` сохраняет такой entry по точному написанию, а при исчезнувшем
источнике `copyEntries` больше не переносит его в результат. Весь Copy
считается успешным, поэтому `fillProfile` заменяет `.copied` пустым списком.
Следующий Clear ничего о сохранённой копии уже не знает.

**Подтверждено через настоящие `Copy` и `Clear`:** правило `FIRST`, на
назначении существовало имя `first` с дополнительным hard link. Первый Copy
успешно перенёс содержимое и вернул одну запись. Источник затем исчез;
правило не менялось. Второй Copy успешно вернул ноль записей, а Clear с этим
результатом оставил скопированное содержимое по прежнему имени `first`.

Проверялось именно имя, записанное первым Copy, а не удаление произвольного
дополнительного hard link, созданного песочницей. Это оставшиеся копии
настроек/credentials после заявленной очистки; побегом из файловой границы
эта находка не является.

**Что исправить:** неопределённость соответствия не должна бесшумно лишать
учёт уже известной копии. Сохранять доказанную прежнюю запись либо явно
останавливать reconciliation, не выдавая неизвестность за отсутствие копии.
Развести требования dedupe и ownership/vouch; простое возвращение прежнего
слияния по file ID снова откроет исправленный дефект.

**Регрессия:** Copy → исчезновение источника → Copy → Clear/`--no-ai`,
с uppercase-написанием, сохранённым неизменным в rules и record, и двумя
hard-link именами на назначении. Записанное имя должно остаться в учёте до
успешной очистки. Контроль: чужое ранее не копировавшееся имя не присваивается.
