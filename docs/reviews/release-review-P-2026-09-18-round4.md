# Release review — P-классификация, раунд 4

Проверенный продуктовый SHA: `c9b835d5f67801ac5d363fbc70073e03874733bc`.
Дата: 2026-09-18. Проверка выполнена в отдельной worktree. Production-код не менялся.

**Вердикт: стабильный релиз блокируется P0-1.** Обновлённая граница лучше покрыта
реальными account-тестами, а прежняя проблема нового HKCU подтверждённо исправлена.
Однако успешный revoke всё ещё может оставить право менять DACL объекта, которым
владеет песочница. Использовать текущую версию как проверенную границу против
враждебной программы нельзя. Опытная эксплуатация с доверенными программами и
резервными копиями возможна, но успешный отзыв доступа нельзя считать гарантией.

Сводка: **P0 — 1 воспроизведённый дефект; P1 — новых не установлено;
P2 — 2 дефекта по статическому анализу, без нового runtime-воспроизведения;
P3 — новых не установлено.** Зелёный CI относится к существующим сценариям и не
опровергает P0-1.

## P0-1 — наличие одного OWNER RIGHTS:RX принимается за полное ограничение владельца

Места: `internal/win/acl/owner.go:363` (`capPresent`),
`internal/win/acl/reclaim.go:142` и `:172` (`takeBack`);
общая проверка используется также в `alreadyCapped`, `owner.go:348`.

`capPresent` возвращает true, как только найдёт одну разрешающую OWNER RIGHTS ACE
с маской `AccessReadExecute`. Остальные ACE этого же SID не проверяются. Поэтому
список, содержащий такую RX-запись и отдельную разрешающую OWNER RIGHTS запись с
`WRITE_DAC`, ошибочно признаётся уже ограниченным. В ветке самостоятельного ACL
без явных ACE account/group `TakeBack` заканчивается успехом, ничего не меняя.

Объект мог получить такой список, пока песочница была его владельцем и каталог
был writable. Это состояние не требует изменения чужого объекта или получения
администраторских прав. Отдельная разрешающая запись сохраняет возможность менять
список прав после отзыва гранта. Это нарушение обещания revoke, а не исключение
про общедоступные каталоги: разрешение адресовано OWNER RIGHTS, а не Everyone/Users.

Измерение выполнено на временных файлах с парным контролем. В обоих случаях
вызывался настоящий `acl.TakeBack`; затем открывался новый handle на `WRITE_DAC`:

| ACL до отзыва | Результат TakeBack | Новое открытие WRITE_DAC |
| --- | --- | --- |
| Только OWNER RIGHTS:RX | success | Access denied |
| OWNER RIGHTS:RX плюс отдельное разрешение WRITE_DAC владельцу | success | success |

Вторая проверка повторена живым дочерним процессом, запущенным через `proc.Run`
с токеном `token.AsSandbox`, включающим собственную identity, как production account
mode. Контроль вернул диагностический код 17 — отказ; дефектная форма — код 23,
подтверждающий получение нового WRITE_DAC handle. Оба процесса действительно
стартовали и завершились без ошибки запуска. Это не старый handle и не отказ
до запуска программы. Изменять чужие ACL или файлы для измерения не требовалось.

Предел измерения: использован текущий неадминистраторский пользователь как владелец
временного файла, не вновь созданная локальная учётка. Отдельный полный CLI/logon
с новой учёткой для этой формы ACL локально не выполнялся. При этом измерены
production-функция отзыва, реальный Windows access check и fully restricted child.

Исправление: решение «cap уже установлен» должно проверять весь эффективный набор
OWNER RIGHTS, включая дополнительные разрешения и inheritance flags. Более простой
безопасный путь для revoke — нормализовать OWNER RIGHTS при каждом обновлении,
не доверяя одной подходящей записи в ACL, который ранее контролировал владелец.
`alreadyCapped` также должен сравнивать конечную политику полностью: сейчас наличие
ожидаемых записей не доказывает отсутствия лишних разрешений.

Обязательная регрессия: настоящий account создаёт объект в RW-гранте; объект имеет
несколько OWNER RIGHTS ACE; прямой revoke без промежуточного RO; новый restricted
процесс не получает WRITE_DAC и не меняет содержимое/ACL. Нужны контроль работающего
процесса, успешного доступа до отзыва и проверка, что возврат старой проверки снова
ломает тест. Включить сценарий в обязательный boundary-список CI.

## P2-1 — учёт копий объединяет разные hard-link имена

Места: `internal/policy/profile/record.go:33`, `fold.go:149`,
`forget.go:109`, вызов из `internal/cli/setup/run.go` (`union`).

Исправление различающихся Unicode-имён корректно уходит от `ToUpper` при определении
принадлежности копии. Но `DedupeEntries` теперь объединяет записи, для которых
`sameEntryPlace` возвращает `os.SameFile`. Это проверка объекта, а не единственности
его имени. Два разных hard link на один файл имеют одинаковый file ID и проходят
эту проверку, хотя удаление одного имени не удаляет второе.

При двух явно перечисленных файловых путях профиля, которые в destination являются
hard links, `union` сохраняет только первую запись. Последующий `Clear` удаляет
только сохранённый путь; второй остаётся с содержимым, но уже без записи в `.copied`.
Это тот же класс неполного удаления копий после `--no-ai`, который ранее проявлялся
на неправильном объединении Unicode-имён. `mirrorFile` открывает существующее имя
с O_TRUNC и не разрывает hard link, поэтому копирование само это состояние не устраняет.

Статус доказательства: установлена цепочка по коду; отдельный runtime-сценарий в этом
раунде не запускался. Семантика нескольких имён и удаления отдельной ссылки описана
в [документации Microsoft](https://learn.microsoft.com/en-us/windows/win32/fileio/hard-links-and-junctions).
Это ошибка учёта/очистки, не новый подтверждённый побег и не обещание отозвать секрет,
который программа уже успела прочитать и скопировать произвольно.

Исправление: для записей последующего удаления различать имя directory entry и
идентичность объекта. Совпадения file ID недостаточно, чтобы выбросить второй путь.
Регрессия должна сохранять два hard-link имени в учёте и проверять исчезновение
обоих при Clear, сохраняя уже добавленные проверки обычных регистровых вариантов.

## P2-2 — --audit пропускает часть общедоступных writable-каталогов

Места: `internal/win/acl/entries.go:226` (`heldBy`), особенно строка 255;
`internal/cli/inspect/audit.go`.

`writableBy` спрашивает, есть ли хоть одно право из маски `changing`. Но `heldBy`
немедленно отвечает false при любом deny, пересекающемся с этой маской. Частичный
запрет, например DELETE, таким образом скрывает отдельное разрешение создавать или
переписывать файлы для того же Everyone/Users. Запрет удаления не запрещает запрос
только на запись; Windows проверяет запрошенные права.

Статус доказательства: статический анализ функции, отдельный runtime-сценарий не
выполнялся. Основание — [описание AccessCheck](https://learn.microsoft.com/en-us/windows/win32/secauthz/how-dacls-control-access-to-an-object).
Изъятие WRITE_DAC/WRITE_OWNER из `changing` здесь не утверждается: эти биты уже есть.
Ошибка — в объединении результата для разных прав.

Это существенно для принятой модели продукта: общедоступные writable-каталоги
остаются исключением, а audit используется для их поиска. Исправление должно
учитывать права раздельно и проверять применимость ACE к текущему объекту.
Нужен тест частичного deny вместе с разрешением другого изменяющего права.

## Проверки исправлений и общий охват

Проверены изменения разрешения членов группы в SID, account/group ACE в Isolate,
TakeBack и StripOwn, pinned-path исключения, текущие owner-rights тесты и обязательный

имеют проходящие реальные account-тесты. P0-1 — дополнительная форма ACL, которую
эти тесты не покрывают.

Прочитаны цепочка account → stub → restricted process, process/thread shield,
передача lease в suspended stub, zero-access/non-inheritable handle, jobs и пути
завершения; init/run/rm, pending grants/revoke/prune; profile copy/mirror/forget,
учёт копий и fingerprint, reserved families/cleanup, CLI audit и release workflow.
Нового подтверждённого побега через запуск, lease, junction или job не установлено.
Это обзор критических цепочек всего проекта, а не доказательство отсутствия всех
возможных ошибок и не повторный независимый запуск каждого Windows-сценария.

Локально на проверенном SHA прошли `go test ./... -count=1 -p 2`, `go build ./...`,
`go vet ./...`, `gofmt -l .` без вывода и `golangci-lint` с 0 issues. Часть тестов
учётных записей/владения локально пропускается по правам машины; PASS пакета не
выдаётся за прохождение каждого такого теста.
