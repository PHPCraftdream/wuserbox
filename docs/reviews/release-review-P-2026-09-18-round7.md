# Release review — round 7 — P0–P3

Проверен `faa7a912ed2751ac03dc5aed699764e9afd9bdd5`, включая изменения после
round 6 и общий путь запуска, выдачи/отзыва прав, управления учётками и
копирования профиля. Production-код этим ревью не изменён.

**Вердикт: релиз блокируется. P0 — 3, P1 — 1, новых P2/P3 нет.**
Два P0 подтверждены операциями над настоящими временными файлами; третий
основан на измеренной коллизии legacy identity и непосредственно следующем
из кода выборе чужой группы. Разрушительный сценарий удаления чужой
учётки для P1 не выполнялся.

Использовать сборку как подтверждённую границу для недоверенных программ
пока нельзя: успешный отзыв ещё не всегда означает запрет нового открытия
файла, а выбор песочницы ещё не всегда проверяет принадлежность проекту.

## P0-1 — revoke сохраняет явный широкий grant, если рядом есть inherited ACE

**Место:** `internal/win/acl/reclaim.go:151–166`.

Исправление round 6 вызывает `carryRevokeEntries` только ниже ветки
`hearsFromAbove`. Если объект принадлежит песочнице и содержит хотя бы одну
унаследованную ACE, эта ранняя ветка убирает записи самой песочницы и
добавляет owner-cap, но оставляет остальные явные разрешения. В частности,
`Everyone:Full Control`, добавленный на собственный файл до отзыва,
сохраняется. Вариант с уже установленным cap выходит ещё раньше.

Это обычная форма файла, созданного внутри writable-каталога: наличие
унаследованных записей не запрещает владельцу добавить собственную ACE.
После отзыва родительского grant у файла по-прежнему могут остаться
унаследованные записи оператора или SYSTEM, поэтому сама ранняя ветка
не исчезает вместе с разрешением группы песочницы.

**Измерено:** временный файл принадлежал SID, переданному в `TakeBack` как
идентичность песочницы. Перед вызовом проверено наличие inherited ACE и
явного Everyone grant. `TakeBack` вернул `nil`; после него
`EveryoneWritable` остался `true`. Затем запущен новый процесс с настоящим
fully restricted token: процесс завершился успешно и изменил содержимое
файла. Это новое открытие после отзыва, а не продолжение записи через старый
handle. Положительные контроли и фактическое изменение содержимого исключают
«процесс не стартовал» и ложное сообщение через недоступный выходной файл.

Существующие `TestTakingAGrantBackNarrowsAnUnexpectedExplicitGrant` и
`TestTakingBackRepairsACappedObjectWithAnUnexpectedExplicitGrant` проходят,
поскольку их исходный ACL защищён и не содержит inherited ACE. Они проверяют
другую ветку.

**Исправление:** применять политику удаления/сужения неожиданных явных
changing grants до обоих выходов inherited-ветки, сохраняя нужное
наследование и восстановление доступа оператору. Наличие cap само по себе
не должно отменять проверку оставшихся ACE.

**Регрессия:** настоящий sandbox account создаёт файл внутри выдачи,
сохраняет наследование и добавляет широкий explicit grant; после отзыва
новый процесс должен получить отказ на запись, удаление и смену DACL.
Проверить отдельно исходный файл с cap и без cap, Everyone и Users,
соседний файл без дополнительного grant и сохранность доступа оператора.
Добавить эти формы в обязательный boundary CI.

## P0-2 — Unicode-folding остался в ACL keep-list и освобождает чужой путь от cap

**Места:** `internal/win/acl/reclaim.go:75–97`,
`internal/win/acl/isolate.go:211–215`,
`internal/win/acl/owner.go:317–323`.

Config/state/prune перешли на новую идентичность пути, но оба нижних слоя,
которые решают, какие принадлежащие песочнице объекты не ограничивать,
по-прежнему используют `strings.ToLower`. `TakeBack` дополнительно сравнивает
root через `strings.EqualFold`.

На проверенном NTFS `K.txt` и `K.txt` — разные записи каталога. Если только
`K.txt` выдан отдельно и внесён в pinned, оба имени попадают в один ключ
keep-list. Отзыв родительской выдачи оставляет `K.txt` без owner-cap и без
снятия его собственного разрешения, хотя отдельной выдачи для него нет.
Для каталога ошибочный `SkipDir` оставляет всё поддерево. Та же коллизия
существует в `capObject` при сужении родительского grant.

**Измерено:** созданы отдельные `K.txt`, `K.txt` и контрольный файл;
`pathid.Same` подтвердил различие первых двух. Только `K.txt` передан в
pinned. `TakeBack` успешно завершился. Контроль получил owner-cap и отказ
на запись, `K.txt` ожидаемо сохранил запись, но запись в неуказанный `K.txt`
также прошла. Проверялся production `TakeBack`, а не отдельная модель
строкового сравнения.

Последующий `Prune` не исправляет эту ошибку: `StripOwn` намеренно
пропускает объекты, принадлежащие самой песочнице, считая, что их уже
обработал cap/revoke. Поэтому исправление только `grant.Prune` недостаточно.

**Исправление:** единая проверенная идентичность directory entry во всех
местах построения и чтения pinned/keep-list, включая исключение самого
root. При ошибке проверки нельзя признавать другой объект отдельно
выданным. Для файла отдельно сохранить различие имён hard links.

**Регрессия:** отдельная выдача `K` внутри writable-родителя, собственные
объекты песочницы внутри отличного `K`; проверить полные `State.Remove`
и writable→read-only lifecycle, включая следующий `Prune`. Законная
вложенная выдача должна сохраниться, Unicode-сосед должен потерять запись,
удаление и WRITE_DAC. Один успешный тест config lookup этого не покрывает.

## P0-3 — legacy fallback выбирает существующую группу без проверки её проекта

**Место:** `internal/sandbox/name.go:39–45`.
Потребители: `internal/cli/setup/prepare.go:118–145`,
`internal/cli/access/target.go:164–177`, `internal/cli/setup/rm.go:51`.

`Name` перебирает legacy-кандидатов раньше нового `existingName` и при
существовании группы немедленно возвращает её. Путь из `group.Comment`
отбрасывается. Проверка совпадения с запрашиваемым проектом не выполняется,
причём эта ветка активна и для существующего проекта, а не только для
восстановления после удаления каталога.

Legacy hash специально сохраняет Unicode lowercasing. Поэтому два разных
пути с одинаковым последним компонентом, например `K/project` и
`K/project` под одним тестовым родителем, дают одинаковый legacy group name.
Если группа первого проекта уже существует, запрос ко второму вернёт её
раньше, чем более строгий код сможет сравнить реальные пути.

**Подтверждено измерением:** два существующих NTFS-каталога различаются по
`pathid.Same`, но их `legacyName` и первый элемент `legacyCandidates`
совпадают. **Статически подтверждён следующий шаг:** ранний возврат
`group.Comment(...).exists` не проверяет comment. Реальная чужая группа
не создавалась и не удалялась в этом ревью; полный account/CLI сценарий
требует elevated regression.

Проверка `s.Dir` через `pathid.Same` в `sandbox.build` защищает конкретный
повторный `--init` с целым state. Она не защищает обычный run и
`access.load`: там state загружается по уже выбранному имени и используется
без сверки проекта. `--rm` также удаляет по этому имени. В результате
команда для одного проекта может использовать или отозвать разрешения
другой песочницы; выдача каталога также адресуется чужой группе.

**Исправление:** legacy-имя должно быть кандидатом для проверки, а не
доказательством принадлежности. Сверять путь группы и доступный state с
запрошенным проектом до выбора identity, сохранить безопасную обработку
исчезнувшего проекта и отвергать противоречивые записи. Общая проверка
нужна всем потребителям, а не только `build`.

**Регрессия:** существующая legacy-песочница для `K/project` и отдельный
`K/project`; `Name`, run, `--grant`, `--revoke` и `--rm` второго проекта
не должны выбирать первую группу, её account, профиль или grants.
Положительный контроль — legacy-песочница всё ещё находится и удаляется
после исчезновения своего настоящего проекта.

## P1-1 — разные sandbox groups могут владеть одним именем учётной записи

**Места:** `internal/sandbox/name.go:83–85`,
`internal/account/account.go:28–46`,
`internal/sandbox/init.go:193–209,263–271`.

Имя группы содержит slug и только 32 бита hash. `account.NameFor` затем
отбрасывает slug и оставляет исключительно эти восемь hex-символов.
Следовательно, различие group names не гарантирует различия account names.
Проверки владельца уже существующей учётки перед её заменой нет.

**Измерено:** для двух настоящих временных каталогов текущий `Name` вернул
`wub-project-140507-3500c0ad` и `wub-project-171370-3500c0ad`.
`account.NameFor` вернул для обеих одну строку: `wub-3500c0ad`.
Получены именно production-результаты после создания этих двух каталогов;
совпадение не подставлялось в тест вручную. Коллизию нашли ограниченной
проверкой identity-строк, без создания множества каталогов или аккаунтов.

**Последствие по коду:** у новой второй песочницы `s.Secret` пуст,
а одноимённая учётка первой уже существует. `replaceUnopenableAccount`
считает её потерянной и вызывает `acct.Delete(name)`, после чего создаётся
новая учётка с другим SID и паролем. State первой песочницы продолжает
содержать старый пароль, а ACL её файлов — старый SID. Это поломка другой
работающей песочницы при обычном `--init` новой. Сам `NetUserDel` для такой
коллизии в ревью не выполнялся.

Для P1 достаточно этой потери identity; обход границы через последующие
повторные инициализации здесь не объявляется измеренным.

**Исправление:** хранить и проверять соответствие group↔account↔project;
никогда не удалять существующий account лишь по совпадению короткого имени
и отсутствию секрета в новой записи. Выбирать уникальное имя с проверкой
коллизий или устойчивый зарегистрированный идентификатор. Изменение схемы
должно сохранить существующие учётки через проверенную миграцию.

**Регрессия:** две разные группы с совпадающим коротким суффиксом;
инициализация второй либо безопасно выбирает другое имя, либо отказывает
до любых изменений. SID, пароль, группы и профиль первой должны остаться
неизменны, и её настоящий запуск должен продолжать работать.

именно на новом SHA.
