# Release review — P0–P3 — 2026-09-17, round 2

## Вердикт

**Стабильный релиз блокирован. Исправление прежнего P0 с правами владельца пока не закрывает production-путь.** Новая защита работает в синтетических тестах, где SID владельца передаётся напрямую, но реальный запуск выдаёт права SID группы; переход от группы к SID её аккаунта реализован неверно. Есть и отдельные непокрытые пути отзыва прав.

Это defensive code review и проверка имеющихся тестов. Нового сквозного воспроизведения побега через реальную локальную учётную запись в этом раунде не выполнялось. Подтверждённый дефект кода не следует выдавать за новый измеренный exploit.

Пользоваться продуктом как проверенной границей против враждебной программы пока нельзя. Для опытной эксплуатации с резервными копиями нужно учитывать, что успешный отзыв или сужение гранта ещё не доказывает потерю доступа к объектам, созданным самой песочницей.

## Что именно проверено

База: `45f102a7ebefa64dd60bee6b992a69bf329f00f8` — checkpoint после отчётного коммита `bce9928`. Исправления пользователя на момент ревью **не закоммичены**: восемь изменённых и четыре новых файла. Они скопированы в отдельную review-worktree и проверены там; исходный checkout не изменялся. В конце проверки контрольные суммы исходных двенадцати файлов совпали со снимком.

Коммит этого отчёта содержит только отчёт, **не проверяемые production-исправления**. Поэтому его SHA нельзя считать SHA протестированного продукта.

Рассмотрены изменения ACL и hive, пути State.Remove/Revoke/Prune, новые реальные account-тесты и CI; повторно просмотрены критические участки копирования/очистки профиля, os.Root, учёт предыдущих копий, process shield и передача lease. Общий suite покрывает остальные пакеты. Это не утверждение об исчерпывающем доказательстве безопасности каждого вызова Windows.

## P0-1 — реальный аккаунт не попадает в список владельцев, которым ставится защита

**Статус:** подтверждено по коду и контрактам Windows API; release blocker. Предыдущее исправление P0 не подключено к обычной выдаче по SID группы.

Места:

- `internal/win/acl/owner.go:121` — `sandboxIdentities`;
- `internal/win/acl/owner.go:132` — `sid.Parse(member)`;
- `internal/win/acl/owner.go:148` — получение участников группы;
- `internal/win/sid/parse.go:15` — преобразование строкового SID;
- `internal/win/acl/isolate.go` и `sweep.go` — условная установка owner cap.

`NetLocalGroupGetMembers` вызывается с уровнем 3. Этот уровень возвращает **имена** вида domain/account, а не SID. Код отрезает доменную часть и передаёт имя в `sid.Parse`, который вызывает `ConvertStringSidToSidW`. Эта функция понимает строковое представление SID и специальные SID-константы, но не разрешает имена аккаунтов. Ошибка молча пропускается.

Следовательно, для штатной группы песочницы список обычно содержит только SID группы. Файлы создаются с владельцем — SID локального аккаунта. Сравнение не совпадает, и новая защита OWNER RIGHTS на эти объекты не устанавливается. Зелёные unit-тесты с напрямую переданным SID владельца этого не обнаруживают.

Контракты подтверждаются документацией Microsoft: [LOCALGROUP_MEMBERS_INFO_3](https://learn.microsoft.com/en-us/windows/win32/api/lmaccess/ns-lmaccess-localgroup_members_info_3), [ConvertStringSidToSidW](https://learn.microsoft.com/en-us/windows/win32/api/sddl/nf-sddl-convertstringsidtosidw).

**Направление исправления:** получать SID участников непосредственно через уровень API, возвращающий SID, либо разрешать полное квалифицированное имя через LookupAccountName. Ошибка определения аккаунта у существующей production-группы не должна превращаться в успешное применение неполной защиты. Учесть время жизни памяти SID.

**Приёмка:** реальная группа и реальный аккаунт; созданный аккаунтом файл; сужение RW→RO; проверка наличия cap, запрета новых изменений и сохранения доступа оператора. Отдельно закрепить разрешение имени участника группы в его SID. Новый e2e-тест подходит по намерению, но требует исправлений из P2-1 и фактического запуска с правами администратора.

## P0-2 — owner cap не охватывает прямой отзыв и автономные ACL объектов песочницы

**Статус:** подтверждённые пропуски в потоках кода; последствия опираются на уже установленную модель owner rights. В этом раунде не воспроизводились отдельной реальной учёткой. Исправление P0-1 само по себе эти ветви не закрывает.

### Прямой RW→revoke

`internal/policy/state/grants.go:140` вызывает `grant.Revoke`, затем `grant.Prune`. Первый снимает записи группы с корня через `acl.Remove` (`internal/win/acl/set.go:167`); второй вызывает `acl.StripOwn` (`internal/win/acl/sweep.go:470`) для потомков.

Ни один из этих путей не определяет владельца и не устанавливает OWNER RIGHTS. Cap существует только в Isolate/sweep. Файл, созданный после последнего sweep, при **прямом** отзыве остаётся без ограничения неявных прав владельца. Обновлённая документация обещает, что следующий revoke закрывает это окно, но код так не делает.

Новый `TestWhatTheSandboxOwnsStaysLockedAfterTheGrantIsGone` сначала выполняет RW→RO и только затем revoke. Даже после исправления разрешения SID он проверяет отзыв уже предварительно capped-объекта; прямую последовательность RW→создание→revoke тест не проверяет.

### Собственная защищённая DACL

`internal/win/acl/owner.go:238`/`:259`: `capObject` пропускает объект, если у него нет унаследованных ACE и служебной метки sweep. Для каталога пропускается всё поддерево.

Такое состояние может создать сама песочница, пока она владеет объектом. Оно не доказывает, что оператор выдал отдельный сохраняемый грант. В результате сужение оставляет в силе прямые разрешения аккаунту и его owner rights. Последующий Prune снимает SID группы, но не прямые записи локального аккаунта. Тест `TestASweepLeavesAnObjectTheSandboxSealedAlone` явно закрепляет сохранение Full Control владельца такого объекта; это несовместимо с общим обещанием отзыва, если владелец — ограничиваемый аккаунт.

**Направление исправления:** применять политику владельца и к revoke; отличать сохраняемые операторские вложенные гранты по доверенному состоянию, а не по изменяемой песочницей форме DACL. Автономная DACL не должна автоматически выводить sandbox-owned объект из обработки. При этом сохранить существующие ограничения чужих/операторских защищённых объектов и права восстановления оператора.

**Приёмка:** независимые real-account сценарии RW→создание→revoke и RW→создание объекта с собственной DACL→RO/revoke. Нужны новые открытия после завершения отзыва; живые ранее открытые handles не являются оракулом для этого свойства.

## P1 — новых подтверждённых функциональных дефектов не добавлено; #174 закрывается только для новых hive

Изменение `internal/account/ownprofile.go:269` добавляет `SUB_CONTAINERS_ONLY_INHERIT = 0x2` всем трём ACE seeded hive. По коду это правильное направление: аккаунт, SYSTEM и Administrators сохраняют прежние маски, а будущие дочерние registry keys получают наследуемые разрешения. Флаг соответствует CONTAINER_INHERIT_ACE. [Контракт EXPLICIT_ACCESS_W](https://learn.microsoft.com/en-us/windows/win32/api/accctrl/ns-accctrl-explicit_access_w).

Однако утверждение «#174 измеренно закрыта» для этого снимка преждевременно:

- `TestWhatTheSeededHiveAnswersItsOwnAccount` локально **SKIP** из-за отсутствия прав администратора.
- CI с изменением наследования ещё не найден; старый зелёный CI относится к прежнему коду, измерявшему отказ.
- `MakeProfile` при существующем NTUSER.DAT возвращает успех без миграции (`ownprofile.go:67`). Старые профили сохраняют известный дефект HKCU до удаления и пересоздания. Это уже честно описано в `docs/limits.md` и исследовании.

Сохраняется прежняя P1-совместимость **для старых профилей**; это известное ограничение обновления, а не вновь обнаруженная регрессия. Для новых hive изменение принимается по анализу кода, окончательная приёмка — по семи успешным операциям нового теста на Windows с правами администратора. Пересоздание профиля нельзя проводить молча: оно затрагивает его локальные данные.

## P2-1 — новая real-account регрессия содержит два неверных оракула

**Статус:** подтверждено по коду теста. На этой машине тело теста не запускалось из-за проверки административных прав.

`internal/e2e/ownright_test.go:62`, `:63`, `:135`: файл создаётся через `cmd echo`, которое записывает завершающий перевод строки, а затем его содержимое сравнивается с константой без перевода строки. Исправная граница тоже даст падение на этом сравнении.

`internal/e2e/ownright_test.go:88`, `:111`, `:149`, `:153`: исходный снимок ACL берётся после RO, затем сам тест законно выполняет revoke/Prune и в конце требует, чтобы ACL совпадала с доревокационной. Удаление записей группы как раз обязано изменить ACL. Проверка смешивает допустимое действие оператора с попытками ограниченного процесса.

**Исправление:** сохранить фактические исходные байты сразу после создания файла; сравнивать ACL до/после запрещённых попыток отдельно в каждой фазе. После законного изменения политики брать новый эталон. Дополнить независимой веткой прямого revoke из P0-2.

## Остальной просмотр и результаты проверок

Копирование не менялось в этом незакоммиченном наборе. Прошли имеющиеся регрессии профиля, включая исправления учёта копий, сопоставления путей/регистра, reserved hive families и ограничения через os.Root. Нового подтверждённого дефекта копирования в этом раунде не получено. Анализ cleanup-масок остаётся уже описанным в продукте ограничением; без нового контрпримера отдельная находка не заявляется.

В просмотренных process shield и передаче lease нового подтверждённого дефекта не найдено. Имеющиеся тесты этих пакетов прошли. Ограничения shared-writable Everyone/Users, сети, интерфейса и ранее открытых handles не пересчитаны как новые P0.

На изолированном снимке успешно выполнены:

- `go test ./... -count=1 -p 2`;
- `go build ./...`;
- `go vet ./...`;
- `gofmt -l .` — пустой вывод;
- `golangci-lint run --config .github/golangci.yml ./...` — 0 issues;
- `git diff --check`.

Повторный адресный запуск **имеющихся** новых account/hive-тестов подтвердил два SKIP из-за отсутствия прав администратора. Поэтому успешный локальный suite не является приёмкой этих двух исправлений.

Один временный диагностический overlay не прошёл компиляцию из-за import cycle и не запускался. Он удалён, доказательством не используется и не меняет результат штатного suite. Новые сквозные security-пробы после этого не выполнялись.

Проверенный удалённый [CI run 35234580302](https://github.com/PHPCraftdream/wuserbox/actions/runs/35234580302) завершился успешно для **3d034275a1cf8345adc82e10fbca7b84ca1e82a5**, до текущих исправлений. Нельзя переносить его зелёный статус на этот снимок. В новом ci.yml перечислено **52** обязательных boundary-теста, но их исполнения на этом коде ещё нет. После исправлений требуется CI именно для коммита продукта, содержащего их, с выполненными account/hive сценариями.

4. Зафиксировать продуктовые изменения и проверить CI этого SHA. Отдельно принять решение о поддержке старых профилей с #174.
5. P3-1: согласовать краткое обещание security policy с актуальной моделью.
